# 《Underground Idle》页面体验、客户端与 WS-RPC

> [返回总目录](README.md) · [上一篇：矿工、远征与新手流程](03-workers-and-expeditions.md) · [下一篇：数据、服务端与内容配置](05-data-and-server.md)

> 文档状态：初始设计，本文所列页面、交互与 `undergroundIdle.*` RPC 均待实施。

## 1. 页面与交互设计

### 1.1 页面结构

首版控制为一个主页面、三个页签和少量弹窗。下表记录目标体验与权威网络边界，不代表现有功能。

| 页面/弹窗 | 主要内容 | 网络行为 |
| --- | --- | --- |
| Underground Idle 主页 | 资源栏、行动力、矿场剖面、产率摘要、收口于底栏的远征摘要 | 进入时拉完整快照 |
| 矿场页签 | 仓库、开采/运输速率、瓶颈、建筑升级 | 写操作成功后整体替换快照 |
| 矿工页签 | 四项属性、岗位、远征/归队状态 | 调岗使用幂等写 RPC |
| 远征页签 | 地点、时长、队伍、奖励范围、产率损失 | 派遣使用幂等写 RPC |
| 离线收益弹窗 | 离线时长、实际收益、满仓/时间上限损失 | 数据来自快照投影 |
| 建筑升级弹窗 | 当前与下级参数、成本、升级后瓶颈 | 不接受客户端上传成本 |
| 编队确认弹窗 | 队伍能力、行动力、归队时间、矿场损失 | 确认后调用 startExpedition |
| 远征结果弹窗 | C/B/A/S、矿石、碎片、事件摘要 | 只展示服务端固化结果 |
| 结果未知弹窗 | 超时、掉线、操作处理中 | 保留原请求 ID 并查询/刷新 |

### 1.2 主界面信息优先级

从上到下建议为：

1. 矿石余额、碎片、行动力；
2. 当前仓库库存/容量和“全部收取”；
3. 矿井剖面及工作矿工；
4. 开采速率、运输速率、有效产率和瓶颈标签；
5. 当前远征状态或“选择远征”，收口于底栏远征页签的角标或短倒计时；
6. 矿场、矿工、远征三个页签入口。

所有长数字应采用统一缩写规则，并可在详情弹窗查看完整整数。按钮禁用必须同时显示原因，例如
“矿石不足”、“行动力不足”“矿工远征中”或“请先领取上一远征”。

主页方案不增加独立的远征摘要卡，以免挤压矿井舞台。空槽时显示远征入口，进行中在底栏显示短倒计时和
行走图标，到达 `endAt` 后改为宝箱图标和“待领取”角标。详情中应展示活动队伍、归队时间、奖励范围和矿场损失。
角标只是服务端时间投影的摘要，不改变自动
归队、领取占槽和快照自愈规则。主界面的构图、状态层与点击语义见
[主界面视觉落地与效果图任务书](08-main-screen-art-brief.md)。

### 1.3 页面状态机

```text
Closed
  → LoadingSnapshot
  → Ready
  → Mutating
  → Ready

Mutating
  → ResultUnknown（TIMEOUT / CONN_LOST / IN_PROGRESS）
  → Reconnecting / QueryOperation / RefreshSnapshot
  → Ready
```

交互规则：

- 同一按钮在 `Mutating` 期间不可重复触发；
- 不同写操作首版也串行，避免玩家在旧快照上连续升级和派遣；
- 写响应携带完整新快照，客户端整体替换而不是拼接多个 delta；
- 迟到响应的 `stateVersion` 小于当前本地版本时直接丢弃；
- 页面关闭、generation 改变或 signal 取消后，迟到结果不能更新旧 View；
- `ResultUnknown` 不是失败，客户端不能换新请求 ID 猜测第一次没有提交。

### 1.4 本地动态表现

客户端收到 `serverNow`、权威库存、当前产率和预计满仓时间后，可以在本地平滑显示数字增长。倒计时也由
本地单调时钟投影。以下情况必须重新拉快照：

- 应用从后台恢复；
- Lobby 断线重连；
- 设备本地时间发生明显跳变；
- 任一写操作完成；
- 状态冲突或操作结果未知；
- 页面重新打开。

客户端不得每秒请求增长数据，也不得把本地投影作为下一次写请求的收益、时间或价格参数。

## 2. WS-RPC 契约规划

### 2.1 路由清单

玩法世界观仍包含“公会”，协议域统一建议为 `undergroundIdle.*`：

| RPC | 读/写 | 幂等要求 | 语义 |
| --- | --- | --- | --- |
| `undergroundIdle.getSnapshot` | 读 | 无需写幂等 | 返回激活状态、服务端时间、权威版本和当前投影快照 |
| `undergroundIdle.activate` | 写 | 必须 | 首次进入时原子创建确定初始档；已激活时回读当前快照 |
| `undergroundIdle.collect` | 写 | 必须 | 结算仓库并全部转入矿石余额 |
| `undergroundIdle.upgradeBuilding` | 写 | 必须 | 先按旧参数结算，再扣费升级 |
| `undergroundIdle.assignWorkers` | 写 | 必须 | 先按旧岗位结算，再原子替换岗位集合 |
| `undergroundIdle.startExpedition` | 写 | 必须 | 恢复/扣除体力、结算矿场、固化远征并离岗 |
| `undergroundIdle.claimExpedition` | 写 | 必须 | 校验时间并只发放一次已固化奖励 |
| `undergroundIdle.queryOperation` | 读 | 无需写幂等 | 按原路由与请求 ID 查询 `pending/applied/unknown` |

首版可以把四座建筑、四名矿工和三个地点作为小型版本化 shared 配置；服务端仍是成本、时长和奖励的
唯一权威。如果配置不随客户端包发布，可在后续阶段增加 `undergroundIdle.getCatalog`。

### 2.2 写请求公共字段

除 `undergroundIdle.activate` 外，所有写请求至少包含：

| 字段 | 说明 |
| --- | --- |
| `clientReqId` | 一个逻辑操作只生成一次，所有重试复用 |
| `expectedStateVersion` | 发起操作时客户端看到的 `idle` 领域版本 |
| 业务最小参数 | 建筑 ID、岗位集合、地点 ID、矿工 ID 或远征实例 ID |

`undergroundIdle.activate` 是唯一特例：它只携带 `clientReqId`，不携带 `expectedStateVersion`。服务端先判断存档是否
存在；不存在才创建版本 1，已存在则天然幂等地返回当前快照，不重置资源，也不因调用方曾看到版本 0 而报
普通状态冲突。

请求中禁止出现：

- uid、区号等可从 Lobby 认证上下文获得的身份；
- 客户端时间、离线时长、完成时间；
- 价格、产率、容量、行动力消耗；
- 成功率、随机种子、结果等级和奖励数量；
- 服务端可从配置与状态推导的冗余字段。

### 2.3 写响应公共字段

所有成功写响应建议返回：

| 字段 | 说明 |
| --- | --- |
| `serverNow` | 本次权威时间 |
| `operationId` | 对应本次逻辑操作/收据 |
| `resultingStateVersion` | 写入后的领域版本 |
| `snapshot` | 完整新快照 |
| `result` | 收取数量、升级前后或远征奖励等操作专属摘要 |

完整快照会增加少量响应体，但首版状态严格有界，换来更简单的断线恢复和客户端一致性，适合 Demo。

同一操作的 `result` 必须保持不变，但重试响应中的 `snapshot` 可能有两种情况：通用 60 秒缓存命中时是第一
次响应的旧快照；缓存过期后领域收据回读时可以附当前最新快照。客户端因此必须分别处理“不可变操作结果”
与“带版本快照”，只应用不低于本地 `stateVersion` 的快照。

操作结果只承诺在文档化的领域收据窗口内可完整回读。超过窗口后，客户端仍必须复用第一次的完整请求；
除 `undergroundIdle.activate` 外，这也包括原 `expectedStateVersion`。服务端可以返回状态冲突或“结果已过期”，但不能
把它静默改写成当前版本的新操作。

### 2.4 版本检查顺序

服务端收到写请求后应遵守：

`undergroundIdle.activate` 先执行上一节的存在性特例；以下顺序适用于其他领域写操作：

1. 规范化并计算 payload 摘要；
2. 先查相同 `clientReqId` 的领域收据；
3. 收据存在且 payload 相同，返回第一次结果；
4. 收据存在但 payload 不同，返回操作冲突；
5. 首次操作才检查 `expectedStateVersion`；
6. 版本一致后执行结算和状态转换；
7. 状态与收据在同一提交边界落地。

“先收据、后版本”保证网络重试携带旧版本时仍能得到第一次成功结果，而不是被误判成普通版本冲突。

### 2.5 结果未知查询语义

`undergroundIdle.queryOperation` 请求包含原始 `operationType` 与 `clientReqId`，响应只允许三种状态：

| 状态 | 含义 | 客户端动作 |
| --- | --- | --- |
| `pending` | 通用幂等占位仍存在，原 handler 可能继续提交 | 保持按钮锁定，退避后再查 |
| `applied` | 已找到不可变结果收据 | 按版本守卫应用结果/快照 |
| `unknown` | 当前既看不到占位也看不到收据 | 不能视为失败；刷新快照并以完全相同请求重试或继续查询 |

由于 handler 超时不会取消迟到副作用，“快照暂时没变化”也不能证明操作失败。要支持 `pending`，
实施前必须为 `undergroundIdle.queryOperation` 增加读取原路由通用幂等占位的受控适配；当前框架没有可直接复用的业务查询接口。

## 3. 客户端实现边界

### 3.1 View/Logic 分层

- `view/` 只绑定 FairyGUI 元素、展示快照和转发点击；
- `logic/` 负责页面状态机、请求编排、版本守卫、本地倒计时和重试；
- Logic 不导入 `cc` 或 `fairygui-cc`；
- 网络通过注入的 WebSocket port 调用，View 不直接访问单例；
- 本地动画和倒计时通过注入的 Clock port 使用单调时间，测试使用假时钟；
- 页面通过 `viewRegistry` 动态 import，不把具体 View 静态引入普通脚本；
- 页面 signal 取消后，任何迟到响应不得继续渲染。

### 3.2 快照应用规则

1. 初始快照建立本地基线和服务端时间偏移；
2. 本地只投影显示值，不修改权威模型；
3. 写成功后以回包完整快照整体替换；
4. 迟到低版本快照丢弃；
5. 版本跳跃允许，说明其他设备或请求已经写入；
6. 状态冲突先刷新，不在旧版本上自动重放可能改变意图的升级或派遣；
7. 断线期间按钮进入结果未知或只读，不伪造成功。
8. 页面保持打开时，秒级 ticker 平时只做本地投影；第一次跨过当前远征 `endAt` 才按
   `expeditionId + endAt` 去重拉一次权威快照，在途期间不并发轮询。

### 3.3 离线摘要

`undergroundIdle.getSnapshot` 可返回一个派生的结算预览摘要：

- 自上次已提交检查点累计的时长（不宣称是玩家实际离线时长）；
- 其中计入收益的时长；
- 仓库增加量；
- 因满仓或 8 小时上限损失的理论量；
- 本次投影跨过 `endAt` 时自动归队的矿工；
- 仍在进行或已经完成待领取的远征；
- 当前行动力与下一点恢复时间。

这个摘要随 `serverNow` 变化，不生成伪稳定的 `reportId`。客户端在本次页面会话只展示一次；它不是经济
真源，也不需要为了关闭弹窗增加一次服务端写。如果之前的写操作已经提交过相同时间段，服务端不承诺重新
构造历史“归队日志”。

## 4. 错误语义与异常场景

### 4.1 可复用现有 RPC 错误

| 错误码 | 本玩法处理 |
| --- | --- |
| `AUTH_REQUIRED` / `ACCOUNT_BANNED` | 进入统一回登录流程 |
| `RATE_LIMITED` | 停止请求并延迟刷新 |
| `INVALID_PAYLOAD` | 非法 ID、重复矿工、未知字段或越界值 |
| `INSUFFICIENT_BALANCE` | 矿石不足 |
| `BUSY` / `STALE_FENCE` | 复用同一请求 ID 有限重试 |
| `IN_PROGRESS` | 进入结果未知并查询操作 |
| `THAWING` | 退避后重试 |
| `USER_DATA_LOST` | 禁止默认值覆盖，提示修复 |
| `INTERNAL` | 通用失败，不泄漏内部信息 |

### 4.2 建议新增的最小稳定错误

当前 shared 错误全集不足以表达挂机领域状态，候选新增：

| 建议错误码 | 含义 |
| --- | --- |
| `STATE_CONFLICT` | `expectedStateVersion` 已过期，客户端拉快照 |
| `OPERATION_CONFLICT` | 同一请求 ID 携带不同 payload |
| `OPERATION_RESULT_EXPIRED` | 原结果已超出可回读窗口；客户端刷新并停止自动重放 |
| `GAMEPLAY_NOT_READY` | 远征未到结束时间 |
| `GAMEPLAY_STATE_INVALID` | 矿工忙碌、槽位占用、任务未解锁等不可直接重试状态 |
| `INSUFFICIENT_STAMINA` | 行动力不足；客户端随后拉快照读取权威恢复信息 |

新增时必须先更新 shared `RPC_ERR_CODES`，再补服务端异常映射、请求/响应 validator 和客户端本地化。客户端
只能按 `code` 分支，不能解析 `msg`。

### 4.3 关键异常矩阵

| 场景 | 期望结果 |
| --- | --- |
| 连点两次收取 | 只入账一次，第二次回第一次收据 |
| 升级请求超时但服务端已提交 | 原 ID 查询/重试得到成功，不再扣一次 |
| 同一 ID 改成另一建筑 | 操作冲突，不返回旧建筑结果冒充成功 |
| 查询得到 `unknown` 且快照未变化 | 不能断言失败或换新 ID；继续查询或以完整原请求重试 |
| 两台设备同时升级 | 只有一个版本成功，另一方刷新 |
| 远征结束前 1ms 领取 | 不发奖、不改状态 |
| 恰好 `now == endAt` | 可以领取，矿工已归队 |
| 完成推送丢失 | 打开页面或点击领取仍得到权威结果 |
| 仓库已满 | 不积累隐藏余数；离线摘要提示损失 |
| 服务器时间倒退 | 不产生负收益，不倒写更早检查点 |
| 活动远征配置被更新 | 继续使用出发时固化版本和结果 |
| 状态 JSON 损坏 | fail-closed，不当作新号覆盖 |
| Redis 写入失败 | 不出现半升级、半扣行动力或错误版本 |
