# 《Underground Idle》指标、测试、路线图与完成定义

> [返回总目录](README.md) · [上一篇：数据、服务端与内容配置](05-data-and-server.md) · [下一篇：美术表现与资产制作](07-art-direction.md)

## 1. 数据指标与调优

### 1.1 玩法指标

| 指标 | 用途 |
| --- | --- |
| 首次收取完成率 | 判断玩家是否理解挂机产出 |
| 首次建筑升级耗时 | 校准初始赠送和成本 |
| 首次远征开始/领取率 | 验证核心闭环是否通畅 |
| 各建筑等级分布 | 观察瓶颈是否过强或失去意义 |
| 各岗位矿工选择率 | 判断属性设计是否形成选择 |
| 各地点派遣率 | 判断时长/奖励性价比 |
| 仓库满仓比例 | 校准容量和回访节奏 |
| 离线 8 小时上限命中率 | 判断硬上限是否过早影响玩家 |
| C/B/A/S 分布 | 校准能力阈值和随机波动 |
| 矿石来源/消耗比 | 防止经济过快膨胀或卡死 |

### 1.2 技术指标

- 每条 `idle.*` RPC 的延迟、错误码和超时；
- `STATE_CONFLICT`、`OPERATION_CONFLICT`、`IN_PROGRESS` 数量；
- 同一请求 ID 命中重试收据的比例；
- 状态 JSON 大小和矿工/收据上限命中；
- 离线结算事件段数与耗时；
- 坏 schema/config 版本计数；
- Redis 锁、fence、写失败和重连次数。

当前框架没有完整线上指标、告警和运营平台；上述是实现与调优需要的观测设计，不是现有交付能力声明。

## 2. 测试与验收

### 2.1 纯公式测试

- 0ms、恰好一分钟、恰好 8 小时和超过上限；
- 多次短结算与一次长结算的定点余数一致；
- 仓库恰好装满、超过容量、初始已满；
- 超出 8 小时后立即再结算不能追回丢弃时间；
- 矿井升级按旧产率、仓库升级按旧容量结算；
- 调岗和派遣在切换前结算旧阵容；
- 远征在离线区间结束时正确分成两段；
- 时钟倒退、未来检查点与 safe integer 上限；
- 行动力恢复、满值、扣除和余数；
- 固定种子、流名和配置版本得到固定奖励；
- 枚举所有合法编队，确认三地点均有可行选择且高级地点不被低级地点严格支配；
- 远征结束点位于 8 小时收益上限之前、恰好相等和之后时，收益窗口与归队状态都正确；
- 生产配置发布边界不会用新配置追溯改写旧离线收益。

### 2.2 协议与服务端单测

- 每条路由的合法、缺字段、未知字段、错类型、越界数组；
- 响应 validator 拒绝漏字段和私有奖励泄漏；
- 相同 ID/相同 payload 串行及并发重复只生效一次；
- 相同 ID/不同 payload 返回冲突；
- 通用 60 秒缓存过期后，领域收据/版本仍阻止二次作用；
- 收据刚被容量或时间窗口淘汰后，完整旧请求不得被再次应用，但不再强求回读原结果；
- handler 超时后的迟到提交能被查询确认；
- `queryOperation` 的 `unknown` 不被客户端解释为安全失败，不能换新 ID 重放；
- 两设备同时收取、升级、调岗、派遣或领取，最终符合某个合法串行顺序；
- 旧 `expectedStateVersion` 不产生新写入；
- 远征临界点提前 1ms 不可领取、恰好结束可领取；
- 覆盖“结束后直接领取”“结束后先调岗再领取”“领取是出发后首次写”，旧返回岗位只应用一次；
- `withUser` cold 重试不会生成两份随机奖励；
- 损坏状态和未知 schema/config 版本 fail-closed。

### 2.3 Redis 集成测试

- 写失败不留下半更新状态或错误 `stateVersion`；
- 锁过期后旧 fence 不能覆盖新持有者结果；
- 同 uid 在 s1/s2 的 `idle` 玩法状态互不影响；
- Redis 重连后能重新读取完整状态；
- 首次无 `idleState` 的玩家由 `idle.activate` 幂等初始化，两个并发激活只得到一份初始资源；
- `idleState` 与两个行动力字段使用一次一致读取，不出现跨写提交的撕裂快照；
- 同一次提交中行动力和 `idleState` 要么都成功，要么都不变。

首版不使用 MySQL，不应为了覆盖技术栈强行制造跨存储集成测试。

### 2.4 客户端无头测试

- 连续双击只产生一个逻辑操作；
- `BUSY/STALE_FENCE` 重试复用原 `clientReqId`；
- `TIMEOUT/CONN_LOST/IN_PROGRESS` 进入结果未知，不生成新 ID；
- 页面关闭后的迟到快照不更新旧 View；
- 低版本迟到响应不覆盖高版本；
- 本地数字和倒计时动画不产生网络写入；
- 应用恢复、重连和推送丢失后通过快照自愈；
- 状态冲突后先刷新，不继续使用旧版本连点升级；
- 倒计时和增长动画只访问注入的 Clock port，假时钟可稳定推进测试。

### 2.5 Creator 人工验收

- 750×1624 下资源栏、矿井剖面和三个页签无溢出；
- 长数字、满仓、行动力不足和任务锁定文案可读；
- 离线摘要顺序清楚，不重复弹出；
- 收取、升级、调岗、派遣、倒计时和领取形成完整闭环；
- 切后台、断线、重连和页面关闭不会产生重复发奖或旧页面回写；
- FGUI 包、动态 View 注册、交互租约和弹窗层级正确。

### 2.6 验证命令建议

实现阶段至少运行：

```bash
npm run typecheck
npm run test:client
npm run test:fgui
npm --workspace @game/server run test
```

涉及 durable Redis、锁和 fence 后，启动本地栈并追加相关集成测试。完整登录链还需要与锁定契约匹配的外部
WebPlatform，不能把无头单测写成端到端通过。

## 3. 分阶段制作路线

### 阶段 0：契约与数值纯函数

- 确定 `idle` 领域名、shared 快照、请求/响应和错误契约；
- 定义领域 `schemaVersion`、`stateVersion`、`configVersion`、`outcomeVersion`；
- 完成生产、容量、体力、远征能力和奖励的纯函数与边界测试；
- 决定并实现幂等 payload 绑定方案；
- 为通用幂等占位补受控查询适配，定义 `pending/applied/unknown`；
- 为 JSON、矿工、远征和收据确定硬上限；
- 更新 shared RPC map、exact validator 与错误全集，运行 `npm run sync:shared`；
- 更新协议指纹并判断是否提升 `PROTOCOL_VERSION`，登记 `ALL_LOBBY_RPC_TYPES`；
- 在 `websocket/idle/<method>.ts` 增加端点，客户端契约完成后运行 `npm run sync:client`。

退出条件：相同输入产生确定结果，全部数值边界可由无头测试覆盖。

### 阶段 1：矿场最小闭环

- `idle.activate` 确定初始化和 `idle.getSnapshot`；
- 矿井、升降机、仓库；
- 离线生产、容量、收取；
- 三类生产建筑升级；
- 主页面和离线摘要。

退出条件：离线、满仓、重复收取和旧版本升级均得到正确结果。

### 阶段 2：矿工与远征

- 四名固定矿工和两类岗位；
- 公会大厅与内容解锁；
- 单远征槽、三地点、行动力；
- 确定性等级与奖励；
- 自动归队、分段离线生产、单次领取；
- 结果未知恢复。

退出条件：派遣与领取回包丢失、并发和重连均不会重复扣除或发奖。

### 阶段 3：表现与完整验收

- FGUI 页面、动画、红点、瓶颈提示和回归摘要；
- 新手任务链；
- Creator 实机/编辑器预览；
- 经济指标和本地诊断日志；
- 全量单测、Redis 集成测试和协议同步检查。

退出条件：新玩家能在不读说明文档的情况下完成“收取—升级—派遣—领取”闭环。

### 阶段 4：可选扩展

- 每日委托与自然日；
- 研究、特质、遗物、负伤；
- 第二远征槽和事件日志；
- 尽力唤醒 push；
- 真正需要时再设计 MySQL 经济、bag effect 或跨玩家能力。

## 4. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 三段生产不易理解 | 玩家只升级矿井却不涨产量 | 明确瓶颈标签、升级前后对比 |
| 远征派人损失不透明 | 玩家认为产量异常下降 | 编队确认显示精确产率变化 |
| 自动归队导致离线分段复杂 | 错把全部时间按最终阵容算 | 单槽、保留岗位、按 `endAt` 有界分段 |
| 幂等缓存不绑 payload | 相同 ID 不同操作返回旧结果 | 实现前增强通用幂等或前置领域校验 |
| RPC 超时但副作用继续 | 客户端误以为失败并再次操作 | 结果未知状态、原 ID 查询、领域收据 |
| 配置热更新改变旧收益/在途任务 | 离线收益被追溯重算，远征结果漂移 | 生产检查点绑定旧版本；远征固化版本和私有结果 |
| JSON 聚合持续膨胀 | 每次写入变大、解码变慢 | 严格上限、收据裁剪、首版无长历史 |
| Redis 被误当生产保障 | 缺备份/容量治理却宣称可靠 | 文档标明当前真源与生产工程化差距 |
| 世界观“公会”与社交 guild 混淆 | 错复用 `guild.*` 协议和字段 | 世界观名词保留，技术域统一 `idle.*` |
| Demo 内容膨胀 | 装备、制造、日常拖慢核心验收 | 严守首版排除清单，阶段 4 再扩展 |

## 5. 首版完成定义

只有同时满足以下条件，才能称《Underground Idle》首版 Demo 完成：

1. 新玩家能完成收取、升级、调岗、派遣和领取闭环；
2. 离线、满仓、8 小时上限和远征自动归队的分段生产计算正确；
3. 客户端时间、收益、成本、种子和奖励均不具权威性；
4. 任一合法写请求在重复、并发、超时或掉线后都不会重复得失资源；
5. 在明确的收据保留窗口内，同请求 ID/同 payload 可回读原结果，同 ID/不同 payload 可识别为冲突；窗口
   外的完整旧请求仍不能被重复应用；
6. 两设备并发操作通过领域版本收敛；
7. 配置更新不追溯改变旧生产区间，也不改变在途远征结果；
8. 坏档和未知版本 fail-closed，不以默认档覆盖；
9. 页面关闭后的迟到结果不会污染新页面；
10. 单元、客户端、FGUI、Redis 集成及 Creator 预览按各自边界完成验证；
11. 文档和产品文案不把开发期 Redis、push、archive、outbox 或本地测试夸大为生产承诺。
