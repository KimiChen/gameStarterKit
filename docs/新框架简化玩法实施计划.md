## 1. 目标与已确认范围

在现有 Cocos 客户端和 `apps/serverNew` 中，以 `gameDemo` kit 交付一组真实存储、可交互的简化玩法，同时验证框架的玩法承载能力与 kit 安装、依赖边界和生命周期。第一版为一个 kit，内部按业务拆分；不拆成多个相互依赖的 kit，也不要求先开发额外插件。

| 功能 | 首版范围 |
|---|---|
| 英雄升级 | 一个英雄；经验丹升级；支持单次/十次操作、等级上限、资源不足部分升级；等级影响攻击力 |
| 商店 | 金币购买药材；少量商品；每日限购；显示余额、库存与剩余额度 |
| 炼丹 | 少量配方和材料；服务端提交即扣料、产丹和计分；客户端整批 2 秒动画；旧计时批次保留领取和余料返还 |
| 冲榜活动 | 默认 10 分钟一轮；炼丹计分；活动结束定榜，按名次自动发奖励邮件；开发入口可提前结束 |
| 邮件 | 收件箱、已读、单封附件领取；离线投递；重复领取不重复发放 |
| 仙盟 | 创建、盟主按玩家 ID 邀请、接受/拒绝、离盟、成员列表；上限 3 人 |
| 多 Boss | 配置 3 个不同 Boss；每种 Boss 同时一个共享房间；玩家选房；同账号同时只在一个 Boss 房间 |
| Boss 恢复 | 服务端进程重启后恢复原血量、伤害记录及阶段，继续原局；不能以重开满血房代替恢复 |
| 客户端 | 使用现有 Cocos 工程；简单列表、按钮与数值；真实调用新服务端 |

首版不包含完整美术、移动寻路、复杂技能、装备、跨服仙盟、同种 Boss 多副本、真实充值或商城支付。普通任务系统不单独扩展，炼丹→冲榜与英雄→Boss 已用于验证功能联动。

## 2. 当前工程事实与实施边界

- `apps/serverNew/engine` 是服务端框架，`apps/serverNew/server` 是业务工程；这是已经迁入的独立实现，不再复制旧 Colyseus 服务端。
- 新服务端使用原生 WebSocket Lobby、Action 生命周期、Redis Bean/Change、模块贡献、Cron 与持久延迟动作。玩家玩法数据默认 Redis 权威，MySQL 保留账号映射和运营/配置用途；不照搬旧服务端的货币 MySQL + outbox 方案。
- 当前有 shop/mail/guild 的 Native Lobby 接入；存在不代表本计划的并发和崩溃要求已满足。逐步写入的扣款/回执、公会归属/成员集合等边界必须实测。
- gameDemo 的 Redis 读取、写入、集合、排行及业务回执均通过框架公开的数据结构封装完成；玩家/实体数据优先使用 `Hash`、`UserHash`、`HashJson` 及其支持的 `DiffArray` / `DiffMap`，其他结构核对现有封装后使用。不得照搬旧 Native Lobby store 中直连 Redis 的路径，不得在 kit 内通过 `.client()`、裸 Redis 命令、自写 Lua 或另造直连 store 绕过封装。
- 保留现有 Task Worker / User Task Worker 的职责和分发路径，使用现有 Action、bindId 和模块贡献接入；暂不统一进程池、重写请求路由或迁移后台任务归属。对现有路径做并发验证，存储一致性仍由封装层保证；发现分发相关限制如实记录，不暗中扩大改造范围。
- `modules/room` 当前主要是旧 Colyseus GameRoom 的票据和定位桥接；`modules/scene/room/SceneRoom.ts` 有内存房间模型，但尚不能据此认定原生持久 Boss 房间已实现。
- 客户端源文件改 `apps/client/src`；编辑器打开 `apps/Cocos`。`apps/Cocos/assets/src` 是生成镜像，不手改。
- 本功能通过显式配置选择 Native Lobby。现有默认 Colyseus Lobby 和 GameRoom 的地址选择保持原意；新增 Boss 由新服务端实际承载，不把它转交旧 GameRoom 来完成验收。
- gameDemo 业务集中在所属 kit 命名空间，服务端采用 §7 的模块落点方案；通用机制归 `server/src/runtime` 或 `engine`，通过公开能力供 kit 消费。不能为了复用，把 gameDemo 业务分散写进宿主 shop/mail/guild 等模块，也不为每个玩法各造一套锁、定时器和同步系统。
- 不读取或恢复 `server/module-library` 归档模块，也不使用 `serverNew/ts-test`。老项目 `/Users/yangdage/workspace/dashentong-server` 只读参考。

以上以 `apps/serverNew/AGENTS.md`、两个项目 README、`engine/docs/development.md` 及 `apps/client/README.md` 为依据。

### 2.1 kit 开发硬边界

- 遵循 [KIT.md](KIT.md) 与 [kit 目录规范](../apps/kits/README.md)。当前所有权推导、服务端 API 与部分生成链主要面向旧 `apps/server`；存在 `kit.json` 不代表已经支持 `serverNew` 的完整包。
- **框架前置单独交付**：补目标运行时识别、serverNew 文件所有权、模块注册与契约生成接入、包测试发现、安装/升级/卸载检查，以及 kit 可调用的资产、提交、调度、同步和房间能力门面。只扩展必要接缝，不改写另一套包管理器。
- **kit 包只包含自己拥有的业务、协议、配置、页面、资源和测试**。不得携带宿主核心覆盖文件、根依赖、环境配置或私自修改启动入口的脚本。缺通用能力先补框架，再由 kit 声明兼容需求；声明格式在 P0 更新 schema 与工具后固化，不把拟议字段当现有能力。
- 金币和背包共用宿主唯一资产权威；邮件若复用宿主持久投递能力，必须通过公开接口。kit 自己定义商品、配方、英雄、活动奖励、仙盟和 Boss 规则，不隐式依赖宿主业务模块内部类或 key。
- 对外 API 面暂定 `growth / production / season / guild / boss`，shared/server/client 按需提供同名门面，各面声明 `version / minSupported`。外部调用只经门面，不导入内部 Action、Bean 和存储实现；第一版商店与奖励编排可保持内部实现。
- RPC 域以 `gameDemo` 为前缀，例如 `gameDemoHero`、`gameDemoAlchemy`、`gameDemoGuild`、`gameDemoBoss`；协议生成和旧/新运行时的路由归属由工具明确处理，不能给旧服务端造假端点来适配包。
- 三个 Boss 是同一玩法的三个配置实例。原生房间的贡献登记在 P0 确定，不能仅填旧 Colyseus `modes` 字段就声称原生房间可安装。
- 数据键的命名空间、区服隔离、业务凭证保留、版本迁移与卸载保留策略必须可登记、可检查；现有 kit 的 SQL/cold archive 机制不能直接当作新服务端 Redis Bean 的实现。生成物由安装后的生成链重建，不把客户端/Cocos 镜像当手写包源。
- 安装操作包文件与生成链，并通过宿主管理记录锁定代码替换；不写运行中的玩法数据，初始化和数据升级走显式生命周期。卸载前停止新业务并检查活动房间、待计分/发奖任务等在途状态，满足退出条件后卸载，数据默认保留，清理需另行显式执行。

## 3. 首版规则与开发默认值

以下是实施默认值，不是老项目数值复刻；P0 固化成配置与测试样例后再编码。

- 开发账号首次进入获得一次性测试金币；另有受开发权限保护的补充资源入口，重复登录不重新发初始资源。
- 商店至少两种材料商品；金币只作为本验证玩法资源。所有模块共用同一钱包/背包权威，禁止商店、炼丹和邮件各建一份余额。
- 一种配方可产两档经验丹，采用服务端随机；耗时按单份计算，批次设数量上限。随机种子/结果与配置版本持久化，重复请求不会重新抽取。
- 英雄一个、等级上限暂定 20，攻击力公式固定为配置驱动的纯函数；战斗中升级在下一次有效攻击时生效，攻击提交需校验所用属性版本。
- 活动 10 分钟，前三名获不同数量金币；按实际获得经验丹的品质与数量计分。同分按达到该分数的先后排序，再以玩家 ID 稳定兜底。
- 活动阶段：`running → settling → settled`。自动发邮件后由玩家领附件，不再另做活动直接领奖，避免两套发奖入口。
- 每日限购按服务端业务日期计算，默认 Asia/Shanghai 00:00；活动使用持久实例 ID 和起止时刻，提前结束不会改变已结束实例的截止时间。
- 仙盟创建者为盟主；有成员时盟主离开自动转给最早加入者，最后一人离开后解散；邀请绑定目标玩家和仙盟，解散或已加入其他仙盟后不能继续生效。
- Boss 首版使用“攻击”按钮和服务端冷却；只保留血量、玩家攻击和伤害排行，不做 Boss 反击与玩家死亡。三个 Boss 有不同名称、血量和奖励。
- Boss 被击杀后进入结算，参与玩家按伤害榜获得邮件奖励，首版每名奖励为 `max(1, floor(Boss 基础金币 / 名次))`。每房当局最多 100 名伤害参与者、100 个当前成员槽位；超出明确拒绝，不静默丢弃记录。默认 60 秒后开启该 Boss 下一局；重启不改变该截止时刻，重放不能重复生成下一局。
- 离开房间保留当局累计伤害。断线只解除连接订阅，不自动删除参与记录；切换房间后旧房请求不能继续生效。

| 炼丹批次 | 炼丹域 | 同次提交完成扣料、产物、批次终态及持久计分事实；旧批次保留结束返还 |
| 活动、积分、定榜结果、发奖进度 | 活动/排行域 | 计分去重、截止检查、定榜、逐人投递状态 |
| 邮件和领取结果 | 邮件域 | 唯一业务来源投递；附件入包与领取标记 |
| 仙盟、邀请、成员关系 | 仙盟域 | 验邀请、容量、玩家唯一归属、成员数；投影可恢复 |
| Boss 局、血量、伤害、冷却、攻击回执 | Boss 域 | 有效攻击全部效果同次提交；死亡只转终态一次 |
| 房间所有权、玩家当前房间、订阅版本 | 房间运行时/所属业务域 | 唯一活跃房间、切换代次、旧进程拒写、恢复重建 |

### P0 固化的资产与配置

- 金币复用 `nativeLobby:shop:balance:v1`，字段 `sid:externalUid`；道具复用 `nativeLobby:grants:items:v1`，字段 `sid:externalUid:itemId`，均落 center Redis。
- 框架公开 `NativeLobbyAssets` 负责上述格式；kit 不直接引用宿主业务类或键。既有 shop 扣款改为同一条件原子结构，避免与 kit 并发覆盖。
- kit 规则真源为 `apps/shared/src/kits/gameDemo/config.ts`：初始金币 5000，经验丹 / 极品丹各 100，进入 demo 自动领取一次（旧账号补发丹药一次）；两种材料价格 10/20，限购 100/50；服务端提交即结算、客户端整批固定播放 2 秒动画（最多 10 炉），高品质概率 25%；英雄上限 100 级，初始攻击 10、每级加 5；榜奖 1000/500/200；Boss 血量 2000/4000/6000。Boss 血量规则从新一局生效，存量局保留原血量和伤害记录。
- 新增 `AtomicHash` 是引擎公开数据结构，使用现有 Redis 实例、类型化编码和全读集条件提交，不属于 kit 私有直连 store。Bean 的延后保存保持原语义。

### 提交机制先验收再复用

1. 审查 Action 调度、绑定路由和 Redis 保存是否能覆盖目标实体。**Action 成功才保存不等于多 key 原子事务；按玩家路由也不等于跨玩家互斥。**
2. 所有业务读写使用封装的 Redis 数据结构。先验证现有 Bean/集合/排行与提交能力；缺少条件原子提交时，在框架封装层补齐“校验余额/版本/归属 → 一起写状态与业务凭证”的公开能力并加契约测试，kit 只调用封装。不得以封装不足为由在业务中直接发 Redis 命令或写 Lua，也不得用新 store 包一层裸命令冒充数据结构接入。
3. 同次 Action 不自动覆盖跨 Redis 实例的原子性。P0 核对各封装结构的实际数据归属；确需跨边界则通过封装持久记录意图、幂等消费、恢复重试，并明确中间状态。所有权与字段变更必须进入现有上下文/提交纪律，不允许 Bean 保存与另一条直写路径竞争覆盖同一数据。
4. 共用现有 Native Lobby 请求幂等机制；领域的批次 ID、邮件来源 ID、攻击 ID 是业务唯一性依据，避免额外维护一套语义冲突的 RPC 缓存。
5. 回复和同步只能发布已提交状态。Bean 走现有 ModSync；其他封装结构需要同步时使用框架认可的公开同步出口，不能另造直写 store 或绕过 Action 中途发成功通知。封装层扩展必须保持提交后才冻结和发送 sync 的语义。
6. 提交后延后事件不自动等于可靠事件；涉及积分和奖励的联动必须可从持久事实重放。通知只负责唤醒，客户端可拉权威全量恢复。

## 5. 多 Boss 房间与恢复设计

### 房间身份与运行方式

- 逻辑身份采用 `sid + bossId + runId`；bossId 区分配置，runId 区分同一 Boss 的各局。配置版本随局固化。
- 三个房间必须是独立运行实例，分别持有阶段、订阅、处理队列和所有权；不能仅用一个页面换三组数值模拟房间。
- 首版通过 Native Lobby 的类型化 RPC 与推送承载进入/退出/攻击/房间状态，不要求一房间一个 socket。推送带 roomId、runId 和递增版本；客户端拒绝旧房及旧版本消息，缺口后拉快照。
- P0 评估既有 scene 执行模型是否可直接承载；能复用则补恢复契约，不能则在现有 Action/模块贡献体系内补最小房间运行时。两种实现都不得依赖旧 `apps/server` 代算 Boss 战。

### 每次攻击的持久边界

服务端校验身份、当前房间代次、runId、攻击 ID、冷却和英雄属性 → 计算实际伤害 → 原子提交血量、累计伤害、冷却、攻击回执、版本及可能的死亡状态 → 回复和推送。

实际计分伤害不超过剩余血量；最后一击不允许血量变负。处理结果未知时用原攻击 ID 查询/重试，不能换 ID 自动补打一刀。

### 重启恢复顺序

1. 读取活动中的 Boss 局索引，取得房间所有权及新代次；旧所有者写入必须被存储侧拒绝。
2. 加载血量、伤害榜、阶段、攻击回执、冷却和配置版本，重建运行实例。
3. `running` 恢复继续攻击；`settling` 续发奖励；`settled` 按已持久化刷新时间推进下一局。
4. 恢复后的首次查询返回完整快照；客户端重连重新订阅，不把进程内连接列表当持久玩家数据。
5. 被杀的 worker 重拉和整个服务进程重启分别验证；旧进程迟到写、旧请求重放不得污染新所有者或下一局。

**恢复承诺**：游戏进程被 SIGKILL、Redis 保持可用时，所有已经返回成功的攻击在恢复后完整保留。保存成功但回复丢失的攻击也只能计一次。Redis 自身断电/丢盘属于另一类容灾，本轮不以此冒充已验证能力；测试仍记录使用的持久化配置。

## 7. 代码与契约落点

以下为 P8 已落实的所有权布局。

| 路径 | 归属与用途 |
|---|---|
| `apps/serverNew/kits/gameDemo/` | kit 清单 `kit.json`、使用说明、能力与数据声明 |
| `apps/shared/src/kits/gameDemo/` | API 门面、公开类型、配置类型、纯公式；shared 保持零依赖 |
| `apps/shared/src/native/lobbyRpc/domains/gameDemo*.ts` | kit 拥有的原生 wire 域，与 API 面的版本关系明确登记 |
| `apps/serverNew/server/src/modules/gameDemo/` | `GameDemoModule.ts` 唯一模块贡献入口；内部 `hero/shop/alchemy/season/guild/boss/rewards` 分域和 `api/<surface>/index.ts` 门面 |
| `apps/client/src/kits/gameDemo/` | kit 入口、API、Logic、View；英雄/商店/炼丹/榜/邮件/仙盟/Boss 页面均归该包 |
| `apps/serverNew/server/test/modules/gameDemo/` | kit 业务测试；按模块与包工具均能发现和运行 |
| `apps/serverNew/kits/gameDemo/verify/` | kit 自有的协议向量、客户端测试、真实服务与故障场景，随包交付 |

- 模块只通过 `GameDemoModule.ts` 贡献路由、启动与调度，生成模块清单，不在 startup 另写第二份清单。业务 Action 直接承载流程，不增加 `*Flow` 层。
- `apps/serverNew/server/src/runtime` / `apps/serverNew/engine` 的改动属于框架前置，单独测试和交付，不归 kit 文件所有权；kit 只通过公开能力消费。
- 原生路由契约测试复用 runtime/protocol 测试接缝；向量归 kit 的 `verify/protocolVectors/`，不写旧服测试目录。
- 客户端登记由 kit 清单及现有 sidecar/生成流程完成；资源、测试、Cocos 镜像与 `.meta` 的所有权按包工具规则推导，生成物不手改、不作为手写制品源。

## 8. 关键验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| 相同写请求重发、同 ID 改参数 | 首次结果可恢复；不重复扣发；改参数被拒绝 |
| 扣金币/材料后关键步骤失败 | 不出现无凭据的损失；原子失败或明确可恢复中间态 |
| 两人争抢资源/名额 | 无超卖、超员、负库存；共享实体与个人归属一致 |
| 炼丹开始后下线并重启 | 已结算产物仍在，重试不重抽奖；旧批次继续计时并保留提前结束返还 |
| 炼丹提交时活动刚好截止 | 按持久化的服务端事件时刻归属活动；定榜需等待截止前事件处理水位完成，避免漏分 |
| 活动任务重复触发/发奖中途杀进程 | 同一活动只定榜一次；续跑不多建奖励邮件；全程无需玩家在线触发 |
| 邮件领取与重试/重启 | 附件只入包一次，已读/已领与实际资产一致 |
| 三个 Boss 同时被攻击 | 各自血量/榜/订阅隔离；某房结算不阻塞其他房 |
| 玩家快速切房/重复进入/旧包迟到 | 同账号唯一当前房间；旧代次攻击拒绝；旧房推送不污染当前 UI |
| Boss 最后一击并发 | 血量归零一次；有效伤害总和正确；同局只发一份结算奖励 |
| 杀房间所在 worker/整个服务 | 恢复相同 runId、血量与伤害记录；已成功攻击不丢、未知结果重试不重复 |
| 原生推送丢失、版本乱序、重连 | 已提交模块 sync 可恢复；房间按版本拉快照；客户端不重复累计 |
| 默认客户端连接回归 | 默认通道选择逻辑与旧 GameRoom 配置不被本功能替换 |
| 干净兼容宿主安装完整 gameDemo 包 | 不借用作者工作区的未打包文件；生成后真实路由、调度、恢复与 Cocos 入口全部可用 |
| API 与文件导入边界 | kit 不导入宿主业务内部或其他包私有文件；越界文件、缺少能力或不兼容 API 在安装/检查阶段拒绝 |
| Redis 数据结构接入 | 业务与初始化写入均经封装；集合变更、持久化、只读保护和提交后同步有行为验证；无绕过封装的直连路径 |
| 带存量数据升级 | 旧玩家档、炼丹批次与 Boss 局按显式版本迁移或拒绝不兼容升级；不得静默重置资产和进度 |
| 有在途业务时卸载 | 活动房间和未完成计分/奖励任务触发退出检查，不能直接删掉处理代码 |
| 排空后卸载并重装 | 路由、菜单、调度等贡献随卸载移除；数据默认保留，兼容重装可恢复；不残留对已删模块的生成引用 |

真实写状态的测试同时检查响应、独立读取的存储结果、消耗/奖励和客户端视图。跨进程测试至少两个 task worker，并确认实际落在不同执行进程；路由 trace 不能代替接收端行为证据。

首轮容量样例暂定三个房间各 10 个模拟玩家并发，另加少量真实 Cocos 客户端；记录吞吐、错误率、响应延迟、事件循环延迟与恢复耗时。P0 依据运行环境确定退出阈值，不能把此样例推断为生产最大容量。

## 9. 检查与交付方式

1. 按阶段刷新 shared、Native Lobby 契约、模块和 Bean 生成记录；新增路由必须有真实实现，不能塞进 PendingRoutes 来伪装启动通过。
2. 新服务端运行目标模块测试及 `pnpm check`；框架修改补 engine 契约测试。使用 server 自身 pnpm 版本，engine 锁文件按其 README 管理。
3. 客户端运行 `npm run typecheck:client`、`npm run test:client`、同步及 `npm run verify:sync`；选择 FGUI 页面时增加相应契约检查。
4. 真实链路使用既有 `verify:native-lobby-live` / `verify:native-lobby-multiprocess-live` 及新增业务场景；复用配置加载和合法测试夹具，不为启动方便另造线路回退规则。
5. UI 按“无头 → 真实服务 → Creator”逐级验证；最终 Creator 仍需覆盖按钮、列表、页面切换、倒计时与多客户端房间同步等引擎边界。
6. 原生域只进入 native 注册表，旧协议注册表保持原样。不得补假端点、缩窄新协议或跳过原生全集校验；旧宿主不需要为 gameDemo 增加识别逻辑。
7. 使用独立 `npm run kit:native -- pack/install/check/test/uninstall` 动线，不调用旧服工具。生成物由安装后重建；框架前置缺失时拒装并说明原因。
8. P7 交付 gameDemo 版本化制品、兼容框架版本、配置说明、数据升级/恢复/卸载说明及验收报告。正式分发仍遵守 KIT.md 的审核与签名规则；本地测试制品不冒称已审核发布。
9. 每阶段记录改动、检查命令、通过证据、未解决问题。最终给出：已有机制直接承载 / 本次新增机制后承载 / 尚未验证，三类能力结论，同时区分框架新增文件与 kit 制品文件。
