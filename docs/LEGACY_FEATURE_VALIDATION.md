# 老项目代表功能与新框架验证方案

调研日期：2026-09-22。老项目：`/Users/yangdage/workspace/dashentong-server`。

本文基于两边源码静态阅读，提取业务行为并设计验证切片；没有运行老项目，也没有实现或验证以下新功能。文中“已有”指源码中存在对应基础能力，不代表完整玩法已经可用。老项目只提供服务端代码，客户端页面是验证建议，不是原 UI 还原。

## 1. 建议选这六组

| 顺序 | 老项目功能 | 最小验证切片 | 主要验证机制 | 当前判断 |
|---|---|---|---|---|
| 1 | 英雄升级 | 一个英雄，单次/十次升级，经验不足部分升级，属性与任务进度变化 | 单玩家多字段提交、配置公式、业务幂等、派生状态 | 有基础，需补英雄域与可靠联动 |
| 2 | 限购商店 + 邮件领奖 | 一件每日限购商品；单封附件领取 | 跨存储扣款发货、限购竞争、离线通知、重试恢复 | 扣款发货/单封领取已有，限购和部分邮件规则需补 |
| 3 | 炼丹 | 一种配方、两种材料；计时、提前结束、返还、产物入包 | 背包与任务原子提交、离线时间、随机结果固化、任务/排行联动 | 时间与锁可复用，背包提交边界需先补 |
| 4 | 仙盟邀请入盟 | 邀请、同意、拒绝、人数上限、离盟、成员通知 | 多实体一致性、共享名额竞争、权限、跨节点推送 | 当前公会是 demo，需补共享实体写入机制 |
| 5 | 炼丹冲榜活动 | 开始→积分→定榜→领奖→未领补邮件 | 活动生命周期、可靠联动、批处理、断点续跑、业务唯一键 | 排行原语已有，完整活动结算需补 |
| 6 | 晚间 Boss | 少量玩家共打一只 Boss，共享血量、伤害榜、结算邮件 | 实时权威状态、动态入场、重连、房间恢复、可靠结算 | 实时房间已有，Boss 持久化和恢复需补 |

前五组检验大厅业务底座，第六组检验实时玩法。不要把“接口能返回成功”作为通过标准：至少要覆盖重复请求、并发、离线及提交中断。

## 2. 英雄升级：单玩家事务与联动

**原代码**：`notice/app/logic/hero/HeroActionUpgrade.php` 的 `doAction` / `calcLevelNum`，以及 `notice/app/logic/user/UserEvent.php` 的 `heroLvUp`。

原行为：单升或十连升；检查功能、爵位和赛季等级限制；结合英雄已有经验与玩家资源计算可升级次数；资源不足时可部分升级并留下经验；重算属性；触发任务；同步场景英雄属性。

**最小实现**：只配一个英雄和一张等级表，保留部分升级、等级上限、属性变化和一条升级任务。爵位、天赋折扣、完整赛季规则后续扩展。

**新框架落点**：shared 放协议、升级计算与配置类型；`websocket/hero/upgrade.ts` 编排；纯玩法档由 `withUser` 提交。客户端做英雄面板，展示等级、剩余经验、资源和任务进度。

**必须明确**：原项目的修为资源在新项目中归哪种资产。若是玩法数值，可与英雄字段同次提交；若归货币权威，则走 MySQL 事务 + outbox，不可先扣款再独立改英雄档。`setField` 效果需考虑已有 `drainPendingFor` 的顺序约束。

**验收**：

- 十连升只够三次时，等级、经验、消耗严格匹配；触及上限不多扣。
- 同一请求重发，尤其提交成功但响应丢失后重发，不再次升级。
- 两个不同请求并发时串行生效，无资源负数、无覆盖更新。
- 升级成功后任务进度与场景属性最终一致；不能因通知失败回滚已提交升级，也不能永久漏任务。

**能力边界**：`core/uow.ts` 能一次写多个 user Hash 字段；`core/idem.ts` 只是短期占位与结果缓存。新增纯 Redis 升级不能只写 `idem: true` 就宣称持久幂等，需要把业务操作标识与变更同次提交，或设计同等可靠的领域去重。任务事实应同事务提交或经持久事件推进，红点可从权威状态重算。

## 3. 限购商店 + 邮件：扣款与发放恢复

**原代码**：`notice/app/logic/shop/ShopActionBuy.php`；`notice/app/logic/mail/MailActionAward.php`、`MailActionAwardAll.php`。

原商店检查开放与解锁、购买次数、扣资源、记购买量、发物品并更新任务/红点。单封领奖检查过期与领取状态，更新已读/已领，处理特殊背包并发附件。

**最小实现**：每日限购一件商品，以金币换普通材料；一封普通道具附件邮件。先完成单封领取，一键领取是有界批处理扩展。

**已有代码**：`core/economy/outbox.ts` 的扣款+intent、Redis 幂等发货及 relayer；`core/economy/mailer.ts` 的邮件领取事务；`websocket/shop/queryOp.ts` 查询发放状态。

**需补**：限购周期及权威计数，应与购买决定一起提交；当前 purchase 只按 SKU 发货，没有每日限购。邮件当前不包含旧项目的过期、特殊背包等完整规则；货币附件在 mailer 注释中明确尚待扩展。

**验收**：

- 最后一次购买额度被两个请求同时争抢，只能成功一次；更换 clientReqId 不能绕过限购。
- 扣款提交后中断进程，重启 relayer 后只发一次物品；客户端先显示发放中，最终刷新余额与背包。
- 已领取邮件换请求号再领也不重复发；离线收到邮件后重新登录可取回。
- 跨日额度按明确的服务端周期计算，不依赖玩家在线时恰好触发定时器。

## 4. 炼丹：离线计时、背包事务、随机与联动

**原代码**：`notice/app/logic/pillRecipe/PillRecipeActionMake.php`、`PillRecipe.php` 的 `pillRecipeResult`。

原行为：校验配方、解锁与数量；扣材料并记录开始时间、数量、材料和双倍奖励信息；领取时按时间算完成量；提前结束则结算完成部分并返还剩余材料；生成产物；推进任务，并按最终实际产物品质增加本服/跨服冲榜分数。

**最小实现**：单队列、一个配方、两种材料、有限数量；保留提前结束、返还、两种可能产物、一条任务和一个积分事件。首版不搬完整藏品、神迹等加成系统。

**时间方案**：持久化批次 ID、开始时间、数量、单件耗时或配置版本；领取时以服务端时间推算，不需要每秒写库。客户端倒计时仅表现。是否需要到时主动通知是另一个需求，不能用进程内定时器代替权威状态。

**关键缺口**：当前 `UnitOfWork` 只提交 user Hash；背包在 bag 分片中。需要能同时“检查材料充足→扣材料→写炼丹批次→记操作 ID”的原子提交路径。现有 `APPLY_EFFECT` 对负数下溢是回补到零并告警，不等于“材料不足则整个请求拒绝”，不能直接用负数 grant 实现配方扣料。

**验收**：

- 开始后退出、重启，再上线仍按原开始时间计时。
- 五份只完成两份时提前结束，产出两份并正确退还余料；立即结束、刚好到时、全部完成分别测试。
- 领取与提前结束并发，只结算同一个批次一次；旧批次请求不能误领新批次。
- 失败重试不重新抽取随机奖励；产物、返还、任务进度与计分事件不会一半成功一半丢失。
- 领取事件重放不重复加榜分。可用固化结果或持久种子+配置版本，不能依赖客户端随机数。

## 5. 仙盟：多实体共享写入

**原代码**：`notice/app/logic/guild/GuildActionInviteRespond.php`、`Guild.php` 和 `notice/app/logic/guildMember/GuildMember.php`。

原邀请响应检查入盟条件、仙盟存在性、容量、邀请归属；同意后新增成员并更新邀请消息状态。该 Action 使用 `ILogicTaskAction`，按 `Guild::getGuildTaskId()` 路由，说明原实现有共享实体执行边界。

**最小实现**：一个仙盟、两个名额、邀请/接受/拒绝/离盟、成员列表与变更通知。

**已有与缺口**：`websocket/guild/join.ts` 明确标注 demo，只改玩家 guildId 并推事件，无真实存在性、审批和容量校验。`withUser(A)` 与 `withUser(B)` 不会互斥，不能保护同一个仙盟最后一个名额。需选定成员关系权威（例如 MySQL 事务与唯一约束）或专门的共享实体串行写模型；玩家 guildId 若作投影，必须可恢复并有一致性策略。

`core/guild/events.ts` 是有限近窗通知，不是成员权威。`websocket/push.ts` 的公会广播目前仅遍历本进程在线索引，不能当作已完成跨节点广播。

**验收**：

- 两人争最后一个名额只进一人；同一人同时同意两个仙盟邀请只归属一个。
- 成员关系提交后进程崩溃，再上线能修复投影；人数与成员表不永久分叉。
- 非本人邀请、无权限操作被拒绝；退出后不继续接收原仙盟业务消息。
- 两个网关上的成员能获知变化；漏通知或超过事件窗口时能全量取回成员状态。

## 6. 冲榜活动：生命周期与中断补结算

**原代码**：`notice/app/logic/activity/rank/ActivityRankFinalize.php` 的 `self` / `run`；`ActivityRankAward.php` 的 `reissue`。炼丹计分来源见 `PillRecipe.php`。

原行为包含个人/仙盟/跨服榜，结束后固化领奖信息，未领奖在后续补发邮件。最小切片只保留本服个人炼丹榜、前三名奖励和未领奖补发。

**已有**：`core/rank/rankService.ts`、`rankScripts.ts` 提供榜与更新原语；`seasonRotation.ts` 提供独立进程和租约先例。但当前轮换主要给旧榜设置 TTL，没有实现上述活动状态机、奖励快照和批量补发。

**需补**：活动实例 ID、开放/截止/领奖时间、截止后的写入规则、结算快照、批处理游标，以及“活动实例+奖励类型+玩家”的唯一发奖标识。定榜与产出积分事件的竞态要明确，例如按事件发生时间归期并设结算水位。跨服榜作为第二阶段，还需区服分组与结果路由。

**注意邮件两层幂等**：现有 `sendMail` 每次新建邮件并随机生成附件操作 ID，只保证同封邮件领取不重复，不能防止结算任务重试创建两封相同奖励邮件。需增加按业务来源唯一投递的入口。

**验收**：

- 活动切换后不串榜；重复积分事件不多加；同分按约定稳定排序。
- 截止瞬间的积分与定榜并发结果可解释、可复现。
- 结算发到一半被杀，重启接着发；双结算进程、重复调度均不重发。
- 手动领奖与邮件补发同时发生也只能取得一份奖励。
- 周期批量处理走独立进程；worker 池只做无 IO 的纯计算，网关不遍历全榜发奖。

## 7. 晚间 Boss：实时房间与持久结果

**原代码**：`notice/app/logic/bossNight/BossNight.php` 的 `settleRank` / `settleUserRank`，以及 `notice/app/event/action/bossNight/` 的结算、重置等动作；调度参考 `notice/app/service/CronManager.php`。

原结算区分个人和阵营排行、Boss 击杀状态，并发送奖励邮件。最小切片只做一只 Boss、少量玩家、共同扣血、个人伤害榜、结束发邮件；首版不搬完整跨服场景、阵营和动态血量调节。

**已有**：`rooms/GameRoom.ts` 有服务端技能计算、Schema 同步、短断线重连和对局证据提交；`core/match/matchConsumer.ts` 有 matchId 去重与持久结算消费。

**需补**：专门的 Boss 房间及活动实例绑定、允许活动中途入场的规则、参与资格鉴权、活动状态持久化、房间恢复及可靠结算生产。当前 demo 开局后锁房，鉴权失败可降为游客，不适合作为奖励房规则直接使用。当前 `emitMatchEvidence` 写流失败仅告警返回 null；“消费者幂等”不解决“生产者没投递成功”。

**验收**：

- 两个客户端同时攻击，血量由服务器统一计算；Boss 死亡只结算一次。
- 伪造伤害、过期资格与重复攻击不能多得奖励；断线重连恢复正确视图。
- 房间进程被杀后按明确策略恢复，或中止并补偿，不能默默丢失活动进度。
- 结算投递失败可持久重试；离线玩家仍收到一次奖励，重复消费不重发。
- 并发压测时同时观察网关事件循环延迟；少量玩家功能通过不代表全服 Boss 容量通过。

## 8. 实施与判断标准

建议先串起：**商店买材料 → 炼丹 → 任务/冲榜 → 活动结束 → 邮件领奖**。这条链的功能复用高，能较快检验单人、跨存储、时间、事件、批处理的完整边界；英雄升级补单玩家复杂计算，仙盟单独验证共享实体，Boss 最后验证实时层。

每个切片交付：shared 契约、配置、端点或房间、必要的存储登记与迁移、最简 FGUI 页面，以及正常/重复/并发/中断验收用例。遵守现有标准动线；不改 net、dispatcher/loader、Main，不手改客户端 shared 生成物。需要扩展 core 提交原语时单独写清契约并按 SERVER.md 规则验证。

记录结果时分三类：

1. **现有机制直接承载**：只增加业务与登记项。
2. **补通用机制后承载**：例如背包条件扣减、共享实体事务、业务唯一邮件、可靠结算生产。
3. **仅功能样例通过**：未完成跨节点、故障恢复或容量验证，不能写成生产能力已验证。

本次结论：新框架有承载这些功能的主要基础组件，但不能据此断言老项目玩法全部直接可迁移。最有价值的验证正是上述事务边界、共享实体一致性、活动补结算和实时房间恢复。
