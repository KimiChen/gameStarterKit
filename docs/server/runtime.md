# 进程、状态与可靠后台执行

> 目标设计，尚需实现与验收；不是当前仓库的完成清单。返回 [最小框架入口](README.md)。

## 按工作性质决定进程

| 角色 | 是否随普通业务启动 | 提供什么 | 如何保持最小 |
|---|---|---|---|
| game 普通业务 | 是 | 统一请求、领域规则、提交、自动同步 | 仅装配选定模块；不持有全服玩家常驻对象 |
| gateway 连接入口 | 初期可与 game 合并 | 连接、会话路由、收发 | 连接负载独立增长时拆分；game 仍验证内部调用身份和业务权限 |
| worker 可靠任务 | 有可靠交付或定时执行时独立启动 | 认领、重试、确认、恢复 | 与 game 共用所需领域代码，通过正式提交规则写入；不复制去重和资产规则 |
| scheduler 定时调度 | 有后台到期工作时启用 | 扫描到期计划并登记任务 | 可与 worker 角色合并；多实例用租约与版本保护，任务标识去重；不在每个 game 中放全服定时器 |
| compute 重计算 | 按需独立启动 | 有界排队和可重做计算 | 输出纯计算结果，正式发奖由领域提交；线程可解 CPU 阻塞，不能代替此处的进程故障隔离 |
| room 实时房间 | 有实时对局时启用 | 局内状态和输入处理 | 与局外数据分开归属，结算使用唯一凭据；默认 game 不加载房间运行时 |
| supervisor 进程托管 | 生产配套，独立于 game | 重启、资源限制、部署与路由摘除 | 使用外部托管工具，可先同机部署，不需要先建复杂集群平台 |

同一仓库和同一制品可以提供不同启动角色，角色的运行依赖和初始化必须隔离。业务逻辑模块允许被 game 与 worker 装配，但同一数据仍有唯一的所有权和写规则；重要交付不能仅依靠进程内事件或易丢通知。

## 外置状态的正确含义

| 数据 | 权威位置 | 业务进程里的形式 | 必须记录的失败规则 |
|---|---|---|---|
| 普通玩家热档 | 按设计由 Redis 保存 | 请求级工作对象；可重建且有容量上限的缓存 | 持久化、禁止误淘汰、备份与故障切换的数据损失窗口 |
| 余额、订单、流水 | 对应 MySQL 领域记录 | 在保护范围内加载的当前值 | 事务、幂等依据、提交结果待查及恢复后核账 |
| 交付依据 | 与权威业务结果原子提交的记录 | 任务编号和当前尝试上下文 | 认领租约、重复消费、超时重试、人工失败清单 |
| 已发布配置 | 受控发布的版本制品 | 经校验的只读快照 | 固定版本、切换规则和外部配置服务故障时的有效期 |
| 房间临时状态 | 房间的当前运行实例 | 局内对象 | 若未建快照／重放则不能承诺无损续局；中断与补偿规则需验收 |

Redis 本身使用内存；“状态不依赖游戏进程”不代表不使用内存，也不代表存储不会丢数据。若业务不能接受目标 Redis 配置的数据损失窗口，必须调整权威存储或持久化方案，不能用进程自动重启来弥补。

## 扩缩容与故障处理的最小协议

| 场景 | 先做什么 | 必须保持的结果 |
|---|---|---|
| 增加实例 | 校验版本和配置，就绪后登记职责／区服／地址 | 路由与通知能到新实例；数据库总连接和请求预算不超限 |
| 缩容 | 标记不再接收新工作，摘除路由，排空并交接租约 | 排空命令可重试、进度可查询；超出排空期限按已定义策略收尾，不能直接假定在途操作失败 |
| 旧实例恢复 | 检查写入资格与版本条件 | 已失效的执行者不能覆盖新状态；客户端重连更新连接位置 |
| worker 中途退出 | 按租约重新认领持久任务 | 业务效果去重后再确认；同一任务可能多次投递，只生效一次 |
| 多进程容量评估 | 对比相同数据和负载的单实例／多实例 | 报告吞吐、延迟、锁等待、存储、CPU 和内存，不预设线性扩容 |

### 17．时间、定时任务与离线补算

玩家不在线或服务器重启后，定时工作仍有明确结果。

参考方向：定时及延迟任务参考 Alloy，借鉴 eerie 的任务管理，吸收 gameKit 的单例保护与重复执行防护。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 17.01 | 统一服务端时间 | 倒计时、过期和每日重置都使用同一时间口径，不能依赖手机时间。 | 基础 |
| 17.02 | 定点及周期任务 | 在指定时刻或周期执行公告、清理、结算等工作。 | 按需 |
| 17.03 | 延迟任务 | 安排几分钟后执行的操作，并保存下来，避免重启后消失。 | 按需 |
| 17.04 | 漏执行补偿 | 停机跨过执行时间后，按业务规则补做、跳过或人工确认。 | 按需 |
| 17.05 | 任务互斥 | 多台机器不能同时完成同一结算；旧执行者失去资格后不能继续写入。 | 按需 |
| 17.06 | 取消和改期 | 任务尚未生效时可取消或改期，已执行的任务要走补偿流程。 | 运营 |
| 17.07 | 时间测试隔离 | 只允许测试环境模拟跨天或活动结束，不能把调时间入口直接开放在生产。 | 运营 |

### 18．可靠队列与跨模块交付

耗时或暂时失败的工作先登记，后台继续处理。

参考方向：可靠交付吸收 gameKit outbox/Stream 的保障，任务入口和管理参考 Alloy，借鉴 eerie 的运维形式；普通异步队列不能直接视为可靠交付。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 18.01 | 任务持久登记 | 任务进入队列前确认已保存，服务重启后仍能找到未完成任务。 | 按需 |
| 18.02 | 业务提交联动 | 扣款等操作与后续交付任务一起登记，避免扣完钱忘记安排发货。 | 按需 |
| 18.03 | 处理确认 | 结果已生效后才确认任务完成；消费者退出后，其他实例可按租约和认领规则接手未完成工作，重复认领不能重复发奖。 | 按需 |
| 18.04 | 重试与等待 | 暂时错误按间隔重试，不持续轰炸有故障的外部系统。 | 按需 |
| 18.05 | 去重与顺序 | 重复投递不重复产生结果；有先后关系的消息按规则处理。 | 按需 |
| 18.06 | 失败处理清单 | 超过重试次数的任务单独列出，保留原因供人工处理，不能直接删掉。 | 按需 |
| 18.07 | 任务看板 | 展示等待量、最久延迟、失败数和处理速度，便于扩容或排障。 | 运营 |
| 18.08 | 受控重放 | 重新执行历史任务前说明影响范围，保留操作者和结果记录。 | 运营 |

### 19．重计算与资源调度

把耗 CPU 的工作移开，避免一次复杂计算让全服卡住。

参考方向：参考 gameKit 计算池的 CPU 隔离，借鉴 eerie 独立任务进程；与业务入口统一接线，不能把普通异步函数当作计算隔离。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 19.01 | 计算任务接口 | 输入和输出格式清楚，业务通过统一入口提交计算。 | 按需 |
| 19.02 | 独立执行资源 | 目标方案把耗 CPU 工作放到独立计算进程，并设置 CPU、内存和队列上限；线程池可在该角色内辅助并行，不代替进程级故障隔离。 | 按需 |
| 19.03 | 并发和排队上限 | 一次只接受资源允许的任务数量，过载时有明确反馈。 | 基础 |
| 19.04 | 超时与资源回收 | 单次计算卡死时终止并回收，不持续占满机器。 | 按需 |
| 19.05 | 计算可重试 | 重新计算不重复发奖；计算结果确认和正式发放是两个步骤。 | 按需 |
| 19.06 | 进度与取消 | 大型任务展示进度，取消后明确哪些部分已经完成。 | 运营 |
| 19.07 | 耗时监测 | 发现某个请求长时间阻塞时能定位到功能与版本。 | 基础 |

### 26．多进程架构、基础设施与扩缩容

明确各类进程职责、数据位置及故障边界，支持同机多核、跨机器和按职责扩缩容，并验证实际容量。

参考方向：借鉴 Alloy 的目标进程、固定区服与会话入口，结合 eerie 多服务及任务进程部署形态；吸收 gameKit 状态权威、并发保护和可靠交付约束。补服务发现、同机多核与跨机扩容、逐角色扩缩容及安全退出；存储外置、进程隔离和性能收益分别验收。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 26.01 | 环境隔离 | 开发、测试和正式数据分开，测试工具不能连错正式数据库。 | 基础 |
| 26.02 | 存储职责规划 | 区分 Redis 玩家热档、MySQL 账本与交付依据，以及进程内可重建对象；分别确定提交、备份、内存淘汰和恢复规则。 | 基础 |
| 26.03 | 连接与资源上限 | 为每类进程设置 CPU、内存、数据库连接、请求队列和后台任务上限；增加实例时也检查共享数据库的总连接与吞吐预算。 | 基础 |
| 26.04 | 容量基线 | 压测得到一台机器或一个区服能承载的连接和操作量，而不是凭感觉估算。 | 基础 |
| 26.05 | 缓存策略 | 缓存失效时能回到正确数据来源，大量同时失效时避免把数据库压垮。 | 基础 |
| 26.06 | 过载保护 | 超负载时优先保证登录、订单等关键链路，非关键统计可以延后。 | 运营 |
| 26.07 | 扩容与数据分布 | 根据连接数、任务积压、CPU、锁等待和存储负载判断瓶颈；决定增加进程、机器或调整数据分布，并用压测证明扩容收益。 | 扩展 |
| 26.08 | 故障切换 | 区分单进程、整机与共享存储故障，分别准备重启、其他实例接管或数据恢复方案；明确可能影响哪些玩家、最多丢多少数据和多久恢复。 | 基础 |
| 26.09 | 成本看板 | 持续观察机器、存储和流量成本，识别闲置资源与异常增长。 | 运营 |
| 26.10 | 多进程职责划分 | 明确网关连接、普通业务、后台任务、重计算和实时房间各自负责什么；每类有独立启停及健康检查入口。连接与普通业务初期可合并，启用的后台任务、重计算、房间及外围系统独立运行。 | 基础 |
| 26.11 | 进程级故障隔离 | 独立进程的异常或内存泄漏尽量只影响自身，其他独立实例继续服务；配资源限额并验证同机耗尽资源时的影响范围。 | 基础 |
| 26.12 | 服务发现与请求路由 | 登记实例的职责、区服、地址和就绪状态，将请求送到合适实例；实例退出或失联后停止向它分配新工作，并更新玩家连接位置。 | 按需 |
| 26.13 | 同机多核与多机扩容 | 同一机器可增加进程使用更多 CPU 核，也可把相同职责部署到多台机器；共享数据、路由和通知在扩容后仍正确，实际收益通过压测确认。 | 扩展 |
| 26.14 | 按角色独立扩缩容 | 按连接数、请求量、队列积压或计算负载，分别增加或减少网关、业务、消费者、计算和房间实例；单例任务仍只由一个有效持有者执行。 | 扩展 |
| 26.15 | 安全缩容与滚动替换 | 实例退出前先不接新工作，等待请求和房间结束或按规则交接，再停止进程；新实例就绪后接流量，避免重复消费、丢通知和旧进程继续写入。 | 按需 |
| 26.16 | 跨进程通信与版本兼容 | 进程之间用明确的消息或调用契约通信，规定超时、结果确认和重试；滚动更新时新旧实例能理解彼此，重要任务不靠内存通知保证交付。 | 按需 |
| 26.17 | Redis 持久化与故障恢复 | 把 Redis 玩家热档与可丢弃缓存分清，配置适用的刷盘、备份和内存淘汰策略；Redis 重启或主从切换时按约定恢复，并实测数据损失窗口。 | 基础 |


## 架构能力与恢复验收补充

普通业务进程尽量不长期持有玩家的权威数据：普通玩法热档主要保存到 Redis，货币账本、订单及可靠交付等按既定职责保存到 MySQL。请求执行时仍需把数据读入内存计算，但业务正确性不能依赖某个进程一直存活。进程异常退出后，应能重新加载已提交状态、继续处理未完成任务，并让客户端重新连接和补齐状态。

以下是拟建设和验收的架构能力，不表示三套参考框架已完整实现，也不承诺任何故障都能靠重启解决。

| 架构能力 | 通俗说明 | 对稳定性与扩展的价值 | 必须满足的条件 |
|---|---|---|---|
| 多进程职责划分 | 连接入口、普通业务、后台任务、重计算和实时房间按职责运行 | 某类工作忙时可以单独增加处理能力，故障也更容易定位 | 启停入口、通信协议、实例归属及资源上限明确；连接入口与普通业务初期可合并；启用的后台消费和重计算使用独立角色 |
| 进程级故障隔离 | 一个独立业务或计算进程退出，其他独立进程可继续工作 | 缩小异常和内存泄漏的影响范围 | 独立进程配资源限额；同机内存耗尽、共享存储故障仍可能影响多个进程；线程池不等同进程隔离 |
| 关键状态外置 | 已提交存档、操作凭据和可靠任务不只保存在业务进程内存 | 替换进程时减少状态搬运及人工修档 | Redis/MySQL 的权威职责、提交顺序、持久化和恢复策略正确 |
| 崩溃自动恢复 | 托管程序拉起进程，初始化完成后重新接流量 | 减少普通进程故障造成的停服时间 | 重试有幂等依据、任务能重新认领、连接能重建；连续崩溃必须限速并告警 |
| 同机多核与多机扩容 | 同机增开进程使用更多 CPU 核，或把实例部署到更多机器 | 随人数增长增加可用处理能力 | 服务发现、路由、跨进程通知和共享写保护已接通；性能提升需要实测 |
| 按职责独立扩缩容 | 连接多就扩入口，任务积压就扩消费者，计算忙就扩计算进程 | 按实际瓶颈增加资源，避免整套服务一起扩 | 消费任务有分片或竞争认领机制；单例任务不能直接复制多份执行 |
| 安全缩容与滚动替换 | 先停止接新工作，等在途工作收尾或交接，再退出旧实例 | 更新版本或减少机器时，尽量减少玩家中断 | 撤销路由、排空、租约交接、旧实例写入保护与版本兼容均通过验证 |

| 进程角色 | 主要负责什么 | 扩容时怎样分配工作 | 重启或缩容时怎样处理 |
|---|---|---|---|
| 网关与连接入口 | 维护连接、认证入口、请求分发和推送 | 新连接分配到就绪实例，记录玩家当前连接位置 | 已有连接通常需要重连；重建连接位置并补齐状态，不能假设连接自动迁移 |
| 普通业务进程 | 加载玩家数据、检查条件、计算并提交结果 | 按区服、玩家或负载路由；同一数据的修改仍用统一并发保护 | 重新加载已提交数据；在途操作按原操作凭据查证或重试 |
| 后台任务进程 | 交付、定时、补算和批量处理 | 可并行任务按分片或竞争认领分配，必须单次执行的任务使用单例保护 | 释放或等待租约过期，由新实例认领；重复到达不能重复产生业务结果 |
| 重计算进程 | 战斗模拟、批量计算等耗 CPU 工作 | 从有容量上限的队列取任务，按 CPU 和排队时间增加实例 | 纯计算可以重做；结果落库和正式发奖仍经过可靠提交 |
| 实时房间进程 | 维护局内状态、输入与对局节奏 | 新房间分配到有容量的实例，已有房间保持明确归属 | 缩容先等房间结束；若需崩溃续局，另建快照、重放或迁移机制；否则按规则中断并处理补偿 |

| 数据位置 | 放什么 | 进程退出后的恢复边界 |
|---|---|---|
| 业务进程内存 | 请求计算对象、只读配置、可重建缓存、连接信息 | 可重新加载或重建；限制缓存大小、对象持有时间和并发，状态外置不等于没有内存问题 |
| Redis | 玩家热档、必要协调信息和需要持久保留的队列等，按职责划分实例或键空间 | Redis 自身是内存数据库，必须配置适用的持久化、内存淘汰及备份策略；刷盘和故障切换仍可能有数据损失窗口 |
| MySQL | 货币、流水、订单、交付凭据及按设计保存的长期数据 | 依赖事务和数据库恢复保障；业务进程重启不能修复数据库损坏 |
| 实时房间内存 | 尚未结算的局内临时状态 | 默认不能承诺重启续局；永久存档与局内恢复分别验收 |

扩容的目标是提高吞吐和故障承受能力，不是保证“进程加倍、性能就加倍”。热点玩家或公会的串行修改、Redis/MySQL 吞吐、锁等待、连接池和网络都可能成为瓶颈。先做容量基线，再逐步增加实例；自动按指标扩缩容属于后续运营增强，不是首发必须依赖的平台。

| 验收场景 | 必须看到的结果 |
|---|---|
| 普通业务进程被终止或因内存上限退出 | 其他独立实例继续服务；退出实例重启并就绪后重新接流量；已提交状态可读取，在途操作可查证且不重复扣款 |
| 提交成功、通知发出前进程退出 | 客户端重连后收到已提交结果，不重新执行一次购买或领取 |
| 后台消费者执行中退出 | 新消费者能认领未完成任务；已生效结果靠凭据去重，最终交付次数正确 |
| 单机增加进程、再增加机器 | 路由和跨节点推送正确；测得吞吐、延迟、存储负载及资源成本变化，明确扩容收益和瓶颈 |
| 缩容或滚动替换实例 | 旧实例不再接新任务，在途业务按规则结束或交接；旧实例恢复后不能继续越权写入 |
| Redis/MySQL 或整台机器故障 | 按独立恢复方案处理，记录实际数据损失和恢复时间；不能拿普通进程重启测试代替存储或主机容灾验收 |

上述职责落到第 06 模块的状态外置、第 25 模块的崩溃恢复、第 26 模块的多进程与扩缩容，以及第 28 模块的对应验收子功能。
