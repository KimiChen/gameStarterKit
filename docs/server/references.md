# 参考来源与原蓝图阅读说明

> 目标设计，尚需实现与验收；不是当前仓库的完成清单。返回 [最小框架入口](README.md)。

目标是让团队既能方便地开发游戏，也能把玩家数据保存正确、把结果及时显示出来，并在上线后有能力维护、排障和处理玩家问题。

常规服务端开发参考 Alloy 的模块、Action、Bean 和 Mod，形成统一的请求处理、数据建模与自动同步链路；结合 gameKit 的安全提交、实时房间和工程检查，以及 eerie-server 的部署与运营经验。

当前工程的演进需遵守已有契约和客户端边界，实际替换网络库、数据层或运行时需要实现和验收。eerie-server 的 PHP/Swoole 运维经验需转化为适合目标工程的方案。

### 各模块的参考来源与职责

| 模块范围 | 参考方向 | 保留或补充其他方案的原因 |
|---|---|---|
| 应用组装、普通网络入口、协议、存档模型、自动同步（01、04～06、08） | Alloy 的模块、Action、协议、Bean/Mod | gameKit 补契约检查与安全提交约束；实时房间单独划分职责 |
| 账号及区服、道具商城、邮件、玩法组织、排行社交、定时配置（02、03、10～13、15～17、20） | Alloy 的模块与业务组织方式 | 身份撤销、支付一致性、可靠领取、结算去重等必须逐项满足；eerie 补运营经验 |
| 后台、权限、监控、部署、基础设施、开发工作台、分析（22～26、29、30） | Alloy 的工具和管理入口 | gameKit 补机检及阻塞诊断；eerie 补部署和运维流程；这不表示 Alloy 已实现表内全部子功能 |
| 安全提交、钱包账本、可靠交付（07、09、18） | 吸收 gameKit 已核对的保障设计，接入统一业务入口 | 这些能力关系到扣款、发奖和故障补偿，不能仅因上层 API 相似就认定等效 |
| 实时房间、重计算、Cocos 客户端（14、19、21） | 参考 gameKit 的专用方案 | 分别解决房间状态、CPU 隔离和引擎界面接入，不要求普通养成接口采用同一技术 |
| 恢复与质量验收（27、28） | gameKit 的数据及故障检查、eerie 的恢复工具，结合 Alloy 的模块入口 | 保留能证明恢复正确的流程和用例，统一操作入口与验收要求 |

| 参考来源 | 重点吸收的长处 | 转化为玩家或团队能理解的价值 | 不能顺带作出的假设 |
|---|---|---|---|
| Alloy | 模块统一登记、HTTP/WS 连接入口、业务 Action、Bean 字段模型、Mod 自动变化同步、后台访问控制 | 连接、操作和数据有统一组织；开发者少写字段转换和重复响应；界面自动跟随数据变化 | 自动保存不天然等于安全事务；实际请求必须接上并发与失败处理 |
| gameKit | 明确的提交边界、用户并发保护、货币账本、可靠交付、共享协议、房间和测试约束 | 不因重复点击多扣钱；开发改错接口时尽早发现；对局及数据有一致规则 | 有这些原语不等于整套系统已经上线验收 |
| eerie-server | 部署模板、进程管理、区服组织、定时/队列、运营与恢复工具形态 | 开服、维护、查单、补偿和恢复有可执行入口，不全靠临时手工操作 | 有脚本不等于已证明高可用；具体语言、旧脚本和密钥处理方式不能直接照搬 |
| 融合后新增的统一规则 | 提交成功后的自动同步、统一权限审计、正式最小测试入口、可复核发布及恢复验收 | 数据正确、界面正确、运营可处理、AI 能验证形成同一条工作链 | 这些是建设目标，尚需实现与测试，不是三者已有能力的简单相加 |

### 阅读表格的方法

| 建设标记 | 含义 | 如何决定是否首发就做 |
|---|---|---|
| 基础 | 适用范围内的最小必要保障 | 首发按所选范围具备；可通过进程内薄接口或外部工具提供，不等于全部内置到游戏核心 |
| 按需 | 某种业务开启后的必要能力 | 没有支付就不用建支付系统；一旦开放付费，验签、对账和售后就是前置要求 |
| 运营 | 持续维护和效率提升能力 | 基础版本先有人工可执行方案，再补看板、批量处理和自动化 |
| 扩展 | 规模变大或产品复杂后再建设 | 例如跨服和合服，不要求单区服首发全做 |

**这 30 个模块是责任划分，不是 30 个独立服务器。** 可以保留同一工程和少量进程；监控、部署、后台及 AI 工具在游戏进程外运行，启用的耗时计算和可靠后台任务也独立执行。也不要求先建 Kubernetes、完整微服务体系或商业监控平台才能上线。
