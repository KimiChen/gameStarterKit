必要能力全部完成

进程内 / 必要执行能力

游戏进程专注处理玩家操作

只装入当前游戏需要的核心与业务。钱包、排行等模块按需选择，不因为框架有这些能力就全部加载。

进程内必须保留

身份与参数校验、权限、并发保护、状态加载与提交、去重依据、提交后的自动同步，以及轻量诊断。

数据怎样流转

受保护地读取 → 检查与计算 → 提交 → 自动同步。普通业务响应只说明本次结果，不重复拼一份玩家数据。

如果游戏进程退出

替代实例重载已提交状态，按原操作编号查证在途结果，客户端重连补齐。未提交修改不当作完成；存储故障另有恢复方案。

进程外 / 观察与告警

监控独立，诊断信息仍然存在

查询历史日志、画曲线、算告警规则，由独立系统完成。游戏进程不运行这些分析与管理功能。

游戏进程提供什么

脱敏日志、有限维度指标、关联编号、健康与就绪状态。采集器还可以直接读取机器和数据库的专用指标。

为什么有助于最小化

监控的存储、查询和升级独立进行，不把日志检索的内存与 CPU 开销放进玩家请求进程。

如果监控停止

普通请求不等待监控恢复。遥测输出有容量限制、采样与丢弃计数；关键权益审计仍需可靠保存，不能一起丢掉。

进程外 / 发布与生命周期控制

外部决定启停，游戏进程配合收尾

发布工具分发固定版本，托管程序负责启动、重启和资源限制。游戏进程无需带部署管理权限。

游戏进程提供什么

当前程序与配置版本、就绪检查、排空入口和进度。排空就是停止接新工作，等待在途工作完成或按规则交接。

怎样更新版本

新实例初始化并就绪 → 接入流量 → 旧实例停止接新工作 → 排空退出。先确认协议和数据兼容，再决定回退。

如果发布平台停止

已运行实例可以继续服务，新发布暂停。独立托管是否仍能拉起崩溃进程，要单独验收；不能假设控制平台失效就完全没影响。

进程外 / 管理与存储维护

后台负责操作流程，业务仍守住数据

页面、审批、查询汇总、配置编辑和备份调度放在外部。它们可以是独立工具，不要求先自建复杂平台。

只读操作

游戏提供有权限、有范围的查询和结果查证。复杂分析在外部做；数据库备份使用存储专用工具，不由玩家请求处理。

会改变状态的操作

封禁、补偿等走明确的业务命令，游戏端检查权限、区服、操作编号和审计。不能给后台一个任意改库的入口。

如果配套不可用

后台停止不阻断普通玩法；已运行实例按有效期使用已校验配置。无有效身份、配置或权威存储时，相关业务必须按规则拒绝或暂停。

开发机 / CI / 隔离测试环境

让 AI 好开发，不把 AI 装进游戏进程

AI 需要的是清晰目录、真实契约、标准示例和能执行的验证入口。线上游戏不需要常驻 AI 开发代理。

工具负责什么

查询接口与字段、修改手写源、生成重复接线、启动隔离环境、执行测试，以及把错误串到具体模块与阶段。

游戏框架提供什么

可查的协议和模块定义、正式初始化入口、稳定错误码、必要关联信息，以及受环境和权限限制的测试接缝。

怎样证明更高效

同样需求、模型和验收条件下，比较手写改动、首次有效反馈、总耗时、人工介入和故障定位结果。这里不预填未经实测的提升比例。

按需 / 独立后台执行

必须完成的工作，要留下可恢复的依据

交付、定时执行和批量补算由独立任务进程处理。没有相关业务的最小应用，不必启动完整任务体系。

游戏进程负责登记

需要跨系统交付时，在权威结果的同一次原子提交中保存交付凭据。不能先扣款，再碰运气把发货任务入队。

任务进程负责执行

认领、执行、重试、确认和失败处理；复用领域规则及正式提交入口，不另写一套奖励与资产规则。

如果消费者退出

未完成任务按租约重新认领，业务效果按凭据去重。任务可能多次到达，但不能因此多发一次奖励。

按需 / 独立计算与房间角色

专用工作用专用资源

重计算与实时房间是两类角色：前者处理耗 CPU 的计算，后者维护局内状态与输入。

重计算

放入有并发、队列和内存上限的独立进程。计算可以重做，正式结算与发奖仍走领域提交入口。

实时房间

有对局需要时再启用，可采用 Colyseus。房间临时状态允许驻留内存，永久资产另有权威来源。

如果房间进程退出

不会因为普通存档在 Redis 就自动恢复整局。续局需要专门的快照或重放；未建设时按约定中断并处理补偿。

最小化有底线：输出接口可以很薄，但权限、提交、去重和必要审计不能省。Redis 也是内存数据库，需要持久化与备份；游戏进程重启不能修复存储损坏。
02 / 目标对应

每一个目标，都能指向一个设计决定。

先说想获得什么，再决定功能和运行位置。不要因为某个功能“上线必需”，就默认把整套系统放进游戏进程。

我们的目标对应的设计如何判断真的做到
核心最小化只装所选模块；监控、发布、后台和开发工具外置。检查启动依赖和资源；外围控制服务停止后，无关玩家请求仍能处理。
业务手写少、AI 好开发统一业务入口、真实接口索引、可运行示例、隔离启动和验证。同一需求下比较手写改动、反馈耗时、人工介入及修复结果。测试代码单列，生成物简单说明。
双端一致、自动同步共用一份协议源；已提交状态由框架同步，界面订阅变化。无需维护两套协议或逐接口拼玩家数据；重连、零值、删除和乱序处理正确。
进程异常后可恢复已提交状态与结果依据外置；请求有保护、重试有去重。提交前后终止进程，重载和查证正确，不重扣、不重发。
多进程可扩缩容按职责增加实例；路由、资源预算、任务认领和排空规则明确。单实例与多实例业务结果一致，并测出实际容量收益与瓶颈。
外围可替换、生产可维护有版本的接口；独立监控、发布与恢复工具；必要审计可靠保留。外围故障可降级，必要依赖失效不误报成功；发布、告警和恢复有演练证据。
03 / 实现与验收顺序

同一次完整交付，内部逐步做对。

先冻结本次交付范围，再按依赖完成。互不依赖的工作可以并行，每部分都要通过约定验收。

一个交付范围 · 多个验证节点

点击步骤阅读；下面展示方法，不是项目实际进度。

01 / 决定最终交付什么

把边界和完成标准放在最前面。

明确目标、模块职责、数据权威、双端协议、进程划分、故障行为，以及这次必须完成的外围配套。详细实现可在验证中修正，变更需说明影响。

本步应交付的结果

一份明确的范围表、接口约定和验收清单。每项能力都有归属，不能等代码写完才讨论“谁负责”。

02 / 证明一次请求可以正确完成

先把一条完整数据链做通。

共用协议 → 权限与参数校验 → 受保护地读取和计算 → 提交 → 自动同步 → 查证与重连。用一个最小业务验证公共机制即可。

本步应交付的结果

正常操作、资源不足、重复请求、提交失败和重连都有可复核结果。只能称“核心链路通过”，还不能称整个框架交付完成。

03 / 证明多进程和故障下仍正确

让实例可以替换，让任务可以接续。

实现角色启动、路由、共享写保护、可靠任务与排空。验证进程退出、消费者重试、增加实例及旧实例恢复等情况。

本步应交付的结果

相同业务在单实例和多实例下保持语义；已提交状态可重载、任务不重复生效，记录恢复边界与实际容量。

04 / 完成这次范围内的配套

把独立系统接上同一套契约。

完成约定的监控、发布、后台命令、备份恢复和 AI 验证工具；接入本次选定的业务能力。接口稳定后，这些工作可与核心实现并行。

本步应交付的结果

外围能独立运行和升级，游戏提供薄接口；选用付费、聊天或房间时，其安全和恢复要求一并完成，不留到上线后再补。

05 / 用完整证据确认完成

范围内的必要能力全部验收。

执行端到端、真实存储、客户端联调、目标容量、故障恢复、发布回退及 AI 开发流程验证。登记实际环境、结果和未覆盖范围。

本步应交付的结果

代码、契约、操作说明、验证证据和已声明的适用边界。只要必要能力仍未完成或存在阻断项，就不能标记为完整交付。

统一完成标准

最小核心 ＋ 本次必需的独立配套 ＋ 已选能力的完整保障 ＋ 全部约定验收。

在本次范围内

可以后写，不能漏交付

例如本次已确定要有监控和备份恢复：实现先后可安排，部署位置可独立，但最终交付前必须完成并验证。

未选用的能力

没有业务需要，可以不装配

例如这款游戏不做实时对局，就无需启动房间运行时。若后续选择启用，再完成该能力的依赖和验收；这与遗漏必要功能不同。

04 / 再确认几个边界

“小”与“完整”，可以同时成立。

一次完整设计，是否意味着一开始就把每行代码都定死？

不需要。先确定范围、职责、数据和接口边界、失败语义及验收标准；具体类、函数和工具可以在实现中调整。涉及共同契约或交付范围的变化，应同步更新设计与验证，不能悄悄绕过。

独立运行，是否就是很多服务器、很多微服务？

不等同。可以同一仓库、同一构建版本，按不同角色启动少量进程；独立进程也可先放在一台机器。进程、机器和共享存储的故障影响不同，需要分别设置预算与验收。监控或部署优先使用合适的现成工具。

游戏进程“只提供接口数据”，是否意味着不能有管理写入口？

观察类能力提供日志、指标和查询就够了。封禁、补偿、维护排空等需要窄范围的命令接口；游戏端仍要验证身份、权限、参数、幂等和审计。业务规则不能搬到后台页面里后就任由它改库。

状态放 Redis，是否所有故障都能重启解决？

不能。普通业务进程可以按凭据查证并重载已提交状态，但 Redis 的刷盘窗口、数据库损坏、整机故障以及未保存的房间状态需要独立恢复方案。多进程也不保证容量按实例数线性增长。
