### 真实缺陷：`joinOwned` 的 abort 监听误杀连接

登录页进入大厅后关闭自身生命周期 context（`loginFlow` 的 `h.close()`），那个 abort 若还挂在大厅连接上，
就会把**刚建立**的连接一起拆掉 → 现象是「登录成功、首屏正常，但之后任何写请求都 `CONN_LOST`」，
看起来像服务端拒绝，实际是客户端自伤。修法：join 控制信号只约束**这一次 join 尝试**
（`detach()` 解绑 + `cancel()` 的 `settled` 守卫），对齐旧 `WebSocketClient.joinOwned` 的
`ready.then(dispose, dispose)`。

**变异验证**：此处**两层**防御。只撤 `detach()` 的 `removeEventListener` → 测试**仍绿**（`settled` 守卫兜住）；
**两层同撤** → **恰好**新增用例红，防矫枉过正的「未落定时 abort 仍须取消」保持绿。逐字还原 + grep 核对

## 多进程 worker 崩溃重拉补证（P5/P8-② 未证② 的第三项）

### 为什么做

P5/P8-② 遗留的「仍未证②」有三项，其中 `worker 崩溃重拉` 是**本机可验证**的那一项：
`userTaskWorkerNum > 0` 与多 task worker 的 `bindId % taskWorkerNum` 分布需要改夹具拓扑（另一件事），
而崩溃重拉只需要硬杀一个进程。它也是进程池设计里**唯一无法靠配置证明**的部分。

### 先查清 alloy-core 的真实语义（不猜）

反编译 `build/alloy-core/index.mjs`（Python `mmap` + `bytes.find`，不要用 shell grep 扫 60s+）：

- `ProcessSupervisor.#handleClosed` 在**非计划退出**且 `#poolReady && !attempt.lifecycleManaged` 时
  调 `#restartAfterClose` → `#spawnSlot(slot)`，即**自动重拉**。
- `#recordRestartFailure` 在 `consecutiveFailures === 1` 时返回 **0** ⇒ 首次崩溃**立即重拉**（无退避）；
  连续失败才 `min(1000, 50 * 2^(n-2))`。`restartStableMs = 30s` 会重置计数。
- 10s 窗口内失败 > `maxRestartsPerWindow = 5` ⇒ `crash_loop_fused` → `requestStop` **停掉整个 runtime**。
  ⇒ 自检里⛔ 只杀一次。
- `WorkerRegistry.beginSpawn`：`generation = previous.generation + 1`、`restartCount + 1`，
  且**在 fork 之前**就 +1。`workers()`（`/health` 的 `workers`）暴露 `{workerId, role, state, pid, generation}`。
- `requestWorkerRestart` 要求 worker 处于 READY/RUNNING ⇒ 已死的 worker 走不到这条，只能靠自动路径。
- 回调侧别：`onWorkerError(workerId, workerPid, exitCode, signal)` 是**主控**侧、意外退出时触发；
  `onWorkerExit` 是 **worker** 侧、只在优雅 drain 时跑（`if (!mux.stopping && initializationSucceeded && !workerExitInvoked)`）。

### 关键发现：崩溃在服务日志里完全无声

全仓 `log/` 里**没有任何** `runtime.process` 行 ⇒ alloy-core 内部的 `context.log` **不落**服务进程 stdout
（日志里只有我们自己 `console.*` 的内容：`fixed sid ... launchMode=multi`、旧通道拒绝、路由痕迹）。
再加上硬杀时 worker 自己的 `onWorkerExit` 跑不到，「崩了又被重拉」在日志里是**零痕迹**的。
⇒ 在 `MultiProcessRuntime` callbacks 补 `onWorkerError`，输出 `workerId/pid/exitCode/signal`。

### 新增场景（`native-lobby-multiprocess-live.cjs` 第 6 条专有场景，总 26 条）

- **刻意杀 task worker**：夹具 `taskWorkerNum: 1` 让 `schedulerOwner` 归 `workerNum` 那个槽位，
  于是这一次崩溃连带考验「重拉后调度器所有权能不能重新拿到」——重启最容易卡住的地方。
- 判「补齐了」用 **`waitForRestart` 四条件同时成立**：同 workerId + pid 变 + `generation` 恰好 +1 +
  状态 READY/RUNNING 且新 pid 存活。只比 pid 会把「槽位标 FAILED、pid 置空」算进去；只比 generation
  会被「spawn 到一半失败」蒙混。
- 另断言：master 未退出、监听进程 pid 与 generation 都没变、原生端点与内网端点仍**只**由同一监听进程绑定、
  重拉出的进程仍是 master 子进程。
- **行为侧**：重拉后发一次 `guild.join`（guildId=1），新增痕迹必须**恰好**一条 `[1, 0, 1]`
  （bindId / source / target），推送由重拉出的 worker 发起。断言「恰好一条」而非「至少一条」——
  重复转发或第二个执行者正是崩溃重拉最可能引入的回归。痕迹按「读日志时刻」切片（日志只追加）。
- 崩溃日志行断言：含 `worker 意外退出` + `workerId=<被杀的那个>` + `signal=9`。

### 变异验证 2 次（逐字还原 + `grep -c MUTATION-PROBE` 核对为 0）

## 多进程：四种角色 + `bindId % taskWorkerNum` 分布（收口未证②的另一半）

### 为什么做

上一条收口了未证②里的「worker 崩溃重拉」，剩下「`userTaskWorkerNum > 0`」与「多 task worker 下的
`bindId % taskWorkerNum` 分布」。两项都要动夹具拓扑，所以合并成一次改动。

### 夹具变化

`bearjoylivemulti/platform.json5`：`workerNum=1 + taskWorkerNum=1 + userTaskWorkerNum=0`
→ **`1 + 2 + 1`**。进程池因此覆盖**全部四种角色**：worker 0 监听原生 Lobby，worker 1/2 是 task worker，
worker 3 是 user task worker（只装载路由表并转发推送，不绑任何端点）。夹具头部注释一并重写，
并把「⛔ 不要退回 taskWorkerNum=1」的理由写在配置里。

### 关键认识：单 task worker 会让分布断言退化成恒真

`taskWorkerNum === 1` 时 `bindId % taskWorkerNum` **恒为 0**，「按 bindId 路由」与「永远发给同一个
worker」在外部观测上完全一样。而「观察到的目标覆盖了全部 task worker」这条断言在那种夹具下会变成
`targets = [1]` vs `taskWorkerIds = [1]` → `deepEqual` 照样通过。**也就是说夹具本身可以让断言空转。**

两道防线一起上：

1. 夹具保持 `taskWorkerNum >= 2`，并在脚本里加 `check(TASK_WORKER_NUM >= 2, ...)` 自检闸
   （放在进程池场景最前面）。夹具与脚本常量必须一起改，不一致时闸**最先**触发。
2. 断言的目标一律**从池里派生**（`health.workers` 的 task worker id、`taskWorkerFor(bindId)`），
   ⛔ 不写死 id；跨进程推送的源也改成「必须是池里真实存在的 task worker」而不是常量。

### 新场景「bindId 分布」

固定公会集合 {1,2,3,4} 对 `taskWorkerNum=2` 取余覆盖两档：1/3 → worker 2，2/4 → worker 1。
协议场景集用掉 2/4，新场景再驱动 1/3，于是「两个 task worker 都真的执行过写」被**观察到**。
断言：四个固定公会的 bindId 都要出现；每条的目标必须等于 `worker_num + bindId % taskWorkerNum`；
观察到的目标集合必须覆盖全部 task worker。实测输出：`bindId → target：1→2 / 2→1 / 3→2 / 4→1（覆盖 2 个 task worker）`。

顺带加强：进程池场景加「workerId 必须覆盖 `0..池规模-1`、各槽位 pid 互不相同」；运营入口场景改为
遍历**所有非监听进程**断言 0 端点（user task worker 也持 `forward` 角色，`lobbyRoleOf` 判错就是
「两个进程抢同一个端口」）；崩溃重拉改为显式挑 `schedulerOwner` 槽位（`workerId === worker_num`），
并让验证用的 `guild.join` **路由到刚被重拉的那个槽位**（否则写会落到另一个没崩的 task worker 上，
证明不了重拉出的进程能用）。

### 变异验证 2 次（逐字还原 + `grep -c MUTATION-PROBE` 核对为 0）

- ⒟ **生产侧把取余路由退化成常量目标**（`worker_num + (bindId % taskWorkerNum)` → `worker_num`）
  → **恰好 1 条红**：`bindId=1 的目标必须等于 worker_num + bindId % taskWorkerNum: 期望 2，实际 1`。
  **而旧的跨进程转发 / 跨进程推送 / 崩溃重拉断言全部保持绿**（bindId 2/4 本来就该落 worker 1）
  ⇒ 旧断言从一开始就分辨不出「取余路由」与「永远发给同一个 worker」。这是本次最有价值的一条证据。
- ⒠ **把脚本常量 `TASK_WORKER_NUM` 退回 1**（模拟「夹具与脚本常量不一致」）→ 3 条红，
  `≥ 2` 闸**最先**触发，另两条是派生目标错位（崩溃重拉 `期望 [[1,0,1]]，实际 [[1,0,2]]`、
  分布 `期望 1，实际 2`）⇒ 常量与夹具是一组**交叉校验**，不一致会响亮失败而不是静默降级。

  controlEpoch / WorldRegistry / 分线分配）** 整套 MMO 框架段（MF0–MF11）搬过来，而 Colyseus WorldRoom 在
  serverNew 里根本没有承载物。
- **真实规模**（旧侧实现体量）：chat `core/chat/{send.ts 102, policy.ts 27}`；party `core/party/{party.ts 214,
  partyScripts.ts 140}`；world `core/world/{enterRpc.ts 140, adminRead.ts 83}`；端点文件 12 个共 155 行。
- **⇒ 结论**：这不是「补齐缺口」，是把**一条在飞的产品线**复制进迁移目标。选项 A 的真实代价远超当时描述。
- **根因再上一层**：shared 的 lobbyRpc registry 是**两代服务端共有的**（MMO 线加域给 `apps/server` 用，
  迁移线拥有其余），而 serverNew 的 `assertComplete()` 假设**自己拥有整份声明面**
  ⇒ **MMO 每加一个域，原生通道就断一次**。party 加入（09-19）起原生通道就没起来过。
- **推荐方案（B 的原则版）**：把判定改成「已注册 ⊆ 声明」+「声明 ∖ 已注册 ⊆ 显式登记的本通道未迁移清单（带原因）」，
  并要求清单项**必须仍在声明面内**（迁移落地后不删清单就 fail ⇒ 自动收紧，不会变成永久旁路）。
  这样：原生通道能启动、income 链条端到端可验、12 条 MMO 域成为**可评审的显式决定**而非静默旁路。
