# 原生 Lobby 业务框架整合施工单

## 1. 目标

原生 Lobby 业务统一复用 Alloy 现有链路：

```text
协议声明
→ 生成 Req/Res、validator、serviceProto、Actions
→ ApiCall 自动实例化 Action
→ ActionUser 自动加载 Bean
→ 业务修改 Bean
→ RedisTask 自动保存
→ ModSync 自动生成变更
→ 当前请求 reply.sync / 其他在线用户 sync
→ 客户端应用模块变更
```

唯一结构差异：协议声明真源位于 `apps/shared/schema/protocols/`，不再手写在 `apps/shared/src/protocol/lobbyRpc/domains/` 或 `server/src/modules/*/*C2S.ts`。

纵向验收业务：`income.claimOffline`（领取离线收益）。

## 2. 固定边界

- 保留 Alloy 的 `IActionLogic`、`ApiCall`、`RouteAction`、`ServerTask`、`ActionUser`、Bean transformer、`RedisTask`、`ModSync`、兼容记录。
- 不新增 Lobby 专用业务接口、业务容器或第二套 Action 生命周期。
- 不恢复旧二进制网关、Protobuf、数字协议号和 PB schema。
- Native Lobby 只负责鉴权、JSON wire 校验、构造 `ApiCall` 和发送结果。
- 默认客户端 Lobby 仍为旧 Colyseus；Native Lobby 仍由显式配置启用。
- GameRoom、Room transport 和实时玩法同步不在本任务范围。
- serverNew 不兼容旧服务端协议、旧二进制入口、旧路由别名、旧 Store 数据格式或旧业务装配；迁移完成即删除旧实现。
- 不为 `apps/server` 保留 serverNew 内部兼容分支；`apps/server` 本身不在本任务内修改业务实现。
- 普通玩家 Redis 业务使用 Bean；禁止长期保留 Bean 与 `*NativeLobbyStore` 双真源。
- SQL/outbox、Lua CAS、ticket、租约、跨玩家共享聚合可保留显式 Store，但必须通过同一 Action 生命周期执行。
- 外部字符串 uid 只用于认证和传输；Bean、bindId、锁使用可信内部数字 uid。
- 生成物禁止手改；兼容记录只能原地推进，禁止删除重建。
- `generated/records/record.json` 保留是因为当前 Bean 持久化和字段编号依赖它，不代表兼容旧服务端传输。
- 不覆盖工作区无关修改。当前 11 个 `*NativeLobbyRoutes.ts` 的未提交修改属于用户改动；实施时先确认其意图，统一入口完成后直接删除对应 Route，不为它们新增兼容层。

### 2.1 禁止的过渡实现

- 禁止同时从旧 TS 协议和 schema 读取同一方向的服务端协议。
- 禁止旧 route → 新 route alias。
- 禁止旧 response → 新 response 适配器。
- 禁止“新 Bean 读不到就读旧 Redis key”。
- 禁止旧 Store 与 Bean 双写。
- 禁止保留未被 Native Lobby、内部 Action、管理入口或生成器引用的旧 Action、协议、路由、Store 和测试。
- 删除前必须用 import、生成注册表和行为测试确认无有效消费者；不得仅凭文件名判断。

## 3. 目标目录与产物

### 3.1 协议真源

```text
apps/shared/schema/protocols/
├── schema-v1.json
├── common/
│   ├── types.json
│   └── errors.json
├── C2S/
│   ├── income.json
│   ├── user.json
│   └── ...
└── S2S/
    └── ...
```

每个 API 必须显式声明：

- `name`：生成 `Req<Name>`、`Res<Name>`、`Action<Name>`。
- `route`：外部字符串路由；Native Lobby 保持当前点号路由，例如 `income.claimOffline`。
- `serviceType`。
- `mode`：`query`、`natural-write`、`idempotent-write`。
- request/response 字段、可选性、范围、长度、枚举和嵌套类型。
- error codes、pushes、contract version。
- `ownerModule`：Action 骨架和模块所有权落点。

### 3.2 Shared 生成物

继续生成并保留现有稳定 import 面：

```text
apps/shared/src/protocol/lobbyRpc/domains/<domain>.ts
apps/shared/src/protocol/lobbyRpc/registry.generated.ts
apps/shared/src/protocol/lobbyRpc/index.ts
apps/shared/src/protocol/lobbyRpc/envelope.ts
apps/shared/src/protocol/lobbyRpc/push.ts
```

其中 `domains/<domain>.ts` 改为 AUTO-GENERATED，包含类型、route 常量和运行时 validator。稳定 façade 不手改业务全集。

### 3.3 serverNew 生成物

```text
server/generated/protocol/server/C2S/serviceProto.ts
server/generated/protocol/server/C2S/actions.ts
server/generated/protocol/server/C2S/mod/**
server/generated/records/record.json
server/generated/records/bean.json5
server/generated/records/proto.json5
```

生成的 `actions.ts` 只从 schema 生成并输出单一 Action 注册表。serverNew 的旧 TS 协议发现入口、旧协议源和仅由其生成的无用 Action 在切换时同批删除，不保留双来源阶段。

### 3.4 Action 落点

schema 中：

```json
{
  "name": "IncomeClaimOffline",
  "route": "income.claimOffline",
  "ownerModule": "income"
}
```

对应：

```text
server/src/modules/income/action/ActionIncomeClaimOffline.ts
```

缺少 Action 时，主动执行生成命令可创建一次骨架；已有文件不得覆盖。检查命令只报告缺失，不修改源码。

## 4. 完成定义

以下条件全部满足才算完成：

- `income.claimOffline` 的协议只在 `apps/shared/schema/protocols/C2S/income.json` 声明。
- shared 类型、validator、registry 和 serverNew `serviceProto/actions` 全部由 schema 生成。
- Native Lobby 不再通过 `IncomeNativeLobbyRoutes` 手工绑定该路由。
- `ActionIncomeClaimOffline` 由生成的 `Actions` 自动找到并实例化。
- Action 继承现有 `GameAction`，通过 `ActionUser` 加载 `User` Bean。
- 领取逻辑只调用 `CopperIncome.claimOffline(user)`。
- `User.copper`、`offlineCopperPending`、`offlineCopperSecondsPending` 由 `RedisTask` 自动保存。
- Action 和业务类不直接调用 `RedisInstance`，不调用 `recordObjectActionSync()`。
- Redis 保存失败时不返回成功、不缓存幂等成功结果、不发送 sync。
- 保存成功后响应包含首次执行结果，`reply.sync` 包含已提交的公开 Bean 变化。
- `offlineCopperPending`、`offlineCopperSecondsPending` 为 `@OnlyRedis`，不得出现在 sync。
- 同一 `clientReqId` 重放返回首次 `{ data, sync }`，不得重复增加铜币。
- 新 `clientReqId` 在无待领收益时返回 0，余额不变。
- income 独立 Redis 账户与手工路由删除，不再写 `nativeLobby:income:account:v1`。
- 不提供 `nativeLobby:income:account:v1` 的运行时迁移、fallback 或双读；开发数据直接清理。
- 客户端收到 `reply.sync` 后更新统一状态，不能只保存最后一个 envelope。
- 单进程和多进程 Native Lobby 验证通过。

## 5. 执行规则

- 每批开始前读取最近 README、`engine/docs/development.md` 和本施工单。
- 每批只做列出的文件和目标，不顺带修复迁移区构建或运行问题。
- 修改 Bean、协议或生成器后必须运行对应生成命令，不手改生成物。
- 生成检查必须在临时目录运行并只读比较；检查命令不得刷新源码。
- 先写或调整失败测试，再实现。
- 每批结束记录实际命令、结果和未完成项；未达到退出条件不得勾选。
- 禁止用源码字符串位置断言代替行为测试。
- 禁止为通过测试保留旧 Store fallback 或双写。

**关键设计决定（改之前先读这几条）**

1. **语言即数据**：字段种类 → 该种类允许的约束键、API/推送/声明的键集合、缺省值（`contractVersion` /
   `required` / 空集合）、上限（嵌套深度、字段数、数组长度、字符串长度、各集合条数）**全在 JSON 里**；
   解析器按它判合法/非法。⇒ 新增种类或约束只改一处，⛔ 不存在第二份白名单。
2. **两道闸（语言闸 ∩ 实现闸）**：`assertKindConstraintKeys` 管「语言允许哪些键」，各 `case` 自己声明
   「真的消费了哪些键」并在末尾再校一次。语言里登记了但解析器没实现的键 ⇒ **拒绝**，⛔ 不是放过去然后
   静默忽略 —— 那会让「schema 写着 `maxLength: 64`、wire 上不生效」变成无声事故。
3. **解析器不放在 `src/protocol/` 下**（放 `src/schema/`）：`scripts/protocol-fingerprint.mjs` 对
   `apps/shared/src/protocol` **整棵树**做字节指纹锁，构建期工具放进去会让「改解析器」看起来像
   「改 wire 协议」、重钉 diff 变成噪声。移到 `src/schema/` 后协议指纹**逐字回到基线**（`--check` 绿、
   `git diff scripts/protocol.fingerprint` 为空）——这就是这次移动正确的自证。
4. **不进 shared 桶导出**（`src/index.ts` 不加 `export *`）：它是生成期工具，进桶会跟着 `sync:shared`
   的镜像被客户端代码拉进打包面。按子路径引用：`@game/shared/schema/index`。
5. **声明形态判定允许判定键同时命中**：域声明可以带 `types`（域内具名类型），纯类型表只有 `types`，
   两者天然撞在一起 ⇒ 胜者由语言文件的 `priority` 决定（⛔ 不在解析器里写死先后）；命中规则还包含
   「该形态的**任一必填键**出现」，这样「漏写 `domain`」报的是「缺少必填键 `domain`」而不是
   一个莫名其妙的「未知键 `apis`」，并在报错里点名另一候选形态。
6. **边界**：本层只管**单文件**规则。跨文件/跨域规则（域名重复、路由全集、operation group 所有权、
   错误码聚合顺序、推送 `type` 冲突）属于生成器（BF2/BF3）——只有它看得到全集。

**字段种类 / 约束 / 元数据的落点**

- 种类：`boolean`、`integer`、`number`、`string`、`enum`、`object`、`array`、`record`、`ref`，
  ⚠ 另加 `json`（比任务列表多一个）：`guild` 域的 `IGuildEvent.data?: unknown` 需要一个
  「不校验内部形状的 JSON 值」种类；缺了它 BF2 迁 guild 时会撞墙并被迫 bump 语言版本。
- 约束：`required`（字段级，缺省 true）、`min`/`max`（integer 安全整数 / number 有限数）、
  `minLength`/`maxLength`、`minItems`/`maxItems`、`members`（enum）、`items`/`values`/`fields`/`ref`。
  **exact object keys 是 `object` 的恒定语义**（wire 上落 `assertExactKeys`），⛔ 没有「允许额外键」的开关。
- 元数据：`name`、`route`、`serviceType`（枚举，取自当前 serviceProto 实际取值）、`mode`、
  `ownerModule`、`contractVersion`（域级与 API 级，缺省 1）、`errorCodes`、`pushes`、
  `ownsOperationGroups` / `exposesOperationGroupTo`（registry 生成需要，见 §3.2）。
- 模式自洽（⛔ 模式不得由「请求里有没有 clientReqId」反推，所以由 schema 显式声明并在此校自洽）：
  `idempotent-write` 的请求必须含**必选** `clientReqId`（string）；`operationGroup`/`inspectable`
  只允许出现在 `idempotent-write`；`inspectable` 必须同时声明 `operationGroup`；
  `inspectsOperationGroup` 只允许出现在 `query`。

**夹具与承重证明**

- 合法：最小 income 声明（3 条路由，覆盖 query / natural-write / idempotent-write）可解析，
  缺省值补齐、**声明序被保留**（生成物稳定性依赖它）；另有数组/记录/枚举/嵌套对象/引用/`json`
  的组合夹具与纯类型表夹具。
- 非法：删必填键、错类型、重复路由/API 名/字段名、未知引用、**环引用**、未知键（含 typo）、
  某种类不接受的约束键、范围自相矛盾、越限、`request/response/push.data` 非 object、
  模式与元数据不自洽、未知 `serviceType`/`mode`、非法路由与标识符形态、枚举成员重复/空/类型错、
  语言文件自身写错（版本/未知键/`requires` 越界）。
- ⚠ **三条用例专门证明语言文件承重**（深拷贝 `schema-v1.json` 改一处再解析）：
  从 `fieldKinds` 删掉一种种类 ⇒ 用到它的声明被拒；从某种类的 `constraints` 删掉一个键 ⇒ 用到它的
  声明被拒；给某种类**加上**解析器未实现的键 ⇒ 该键仍被拒（不静默忽略）。⛔ 不许改成「断言解析器里
  某个常量」——那样只能证明解析器自洽。

- **口径 B**：不加钩子，全部用声明式约束表达 ⇒ 必须把 kit/economy 的校验器内联进语言（与 kit api 面重复真源），且跨字段不变量（棋盘顺序、tiles 顺序）仍需专门约束。

**关键设计决定（改之前先读）**

1. **`external` 必须同批声明 `check`**：外部类型没有生成物可依据的形状，形状**由具名校验器独占产出**，生成物只渲染 `fn(raw, path)`。⛔ 不允许「external + 声明式字段」两处描述同一形状。
2. **`check` 与 `items`/`fields` 互斥**（生成器硬闸）：同一节点既写 `check` 又写形状键 ⇒ fail-fast，否则形状有两份真源且只有一份生效。
3. **`from` 相对声明文件自身**（`../checks/<域>`、`../economy`、`../../../kits/<kit>/api/<面>/index`），由 `assertRelativeSpecifier` 强制；⛔ 不得绝对或裸 specifier（否则生成物里出现指向包外的路径）。
4. **`legacy/` 整目录删除**：13 个手写域 + 非路由导出搬完后，`legacy/` 已无消费者（`registry.generated.ts` 无引用），一次删净；`ARENA_SHOP_BOOST_COST` / `CHAT_TEXT_MAX` 搬进 `checks/`，三端消费点改 import。
5. **生成物形态**：`function parse<类型名>(input, path): <类型名>`（返回**具名类型**，⛔ 不展开成结构字面量——空对象会退化成 `{  }`）；`record` 渲染用中间变量 `Record<string, T>`（直接赋进 `readonly` 索引签名对象报 TS2542）；`assert` 包成 IIFE；push 入口是 `parseX(pushRecord(input, "push.data"), "push.data")`。
