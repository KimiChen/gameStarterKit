# Lobby 业务协议兼容基线

> 适用范围：`apps/serverNew` 迁移到原生 WebSocket Lobby 时保留的**业务**契约。
>
> 不覆盖实时 GameRoom 的状态同步和玩法 C2S/S2C。旧的 Colyseus Lobby、数字协议号、二进制包头和 Protobuf
> 不是本次兼容对象。

## 唯一真源

| 内容                                                | 真源                                                                                              |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| RPC 路由、请求/响应 validator、执行模式与业务错误码 | `apps/shared/src/protocol/lobbyRpc/domains/*.ts`、`coreErrors.ts`，生成到 `registry.generated.ts` |
| 业务请求/响应信封                                   | `apps/shared/src/protocol/lobbyRpc/envelope.ts`                                                   |
| 原生 WebSocket 外层帧、连接状态与限制               | `apps/shared/src/protocol/lobbyRpc/transport.ts`                                                  |
| 领域推送与强制下线关闭码                            | `apps/shared/src/protocol/lobbyRpc/push.ts`                                                       |

`registry.generated.ts` 是生成物。服务端和客户端都必须调用 shared runtime validator，不能维护第二份
路由或字段清单。

## 原生 WebSocket wire

Lobby 使用独立于 GameRoom 的明确 WebSocket URL。它可由显式本地开发配置或后续目录字段提供，但必须声明
transport kind；不能从共用的 `gameWsUrl` 推导、把它改为裸 WebSocket 地址，或静默回退。默认配置继续走
Colyseus；只有显式 `native-websocket` 配置才可指向 `serverNew`。

传输层版本是 `LOBBY_TRANSPORT_VERSION = 1`，与每条 RPC 的 `contractVersion` 分离。帧为严格 JSON
文本帧，最大 64 KiB；二进制帧、未知字段、未知 kind 和不兼容版本均 fail-closed。完整类型和 validator
以 `transport.ts` 为准，核心方向如下：

```text
client → auth { v, kind:"auth", token, sId, reconnect? }
server → auth.ok { v, kind:"auth.ok", uid, sId }
server → auth.error { v, kind:"auth.error", err:{code,msg} }

client → rpc { v, kind:"rpc", rpc:{id,type,payload?} }
server → reply { v, kind:"reply", reply:{id,ok,data?|err?} }
server → push { v, kind:"push", push:{type,data} }
either → ping/pong { v, kind, nonce }
server → control.error / close
```

认证必须在第一条业务 RPC 前完成。token 只允许位于 `auth` 控制帧，不得进入 URL、日志或业务 payload。
每条 RPC 都要复验会话；uid 和 sId 来自可信认证上下文，不能被 payload 覆盖。重连再次走 `auth`，不能复用
旧连接的身份结果。服务端的数值 uid 与 shared 字符串 uid 必须以无损映射关联，禁止 `Number(uid)`。

## 保留的业务信封

内层业务信封没有变化：

```ts
interface IRpcEnvelope {
  id: string;
  type: string;
  payload?: unknown;
}
type IRpcReply =
  | { id: string; ok: true; data?: unknown }
  | { id: string; ok: false; err: { code: RpcErrCode; msg: string } };
type LobbyPushEnvelope = {
  type: LobbyPushType;
  data: LobbyPushMap[LobbyPushType];
};
```

- `id` 只用于请求/响应配对；业务写入仍使用 `clientReqId`。
- 请求、响应与推送都需经所属 shared validator 严格校验；未知字段不得先剔除再执行。
- 未知路由返回 `UNKNOWN_TYPE`；服务端产生不合法响应返回固定文案的 `INTERNAL`。
- `user.getInfo` 成功时 `data.user` 必须存在，不能返回 `null`。
- wire 错误码只能是 shared 的字符串 `RpcErrCode`；不得暴露旧 `MsgError.code` 或其他内部数字码。

## 生命周期、安全与幂等

- RPC 观察时限 15 秒；handler 预算 10 秒；超时不代表底层写入已取消。
- 令牌桶默认容量 20、每秒补充 10；超限返回 `RATE_LIMITED`。
- 断线立即结算 pending RPC 并拒绝离线发送；传输层不得自动重放写请求。
- 幂等键至少绑定 `uid + sId + route + clientReqId`。同键异 payload 返回
  `OPERATION_CONFLICT`；结果不可回放时返回 `OPERATION_RESULT_EXPIRED`。
- 强制下线先发 `auth.forceLogout`，再按 `push.ts` 使用 4901（封禁）、4902（顶号）或
  4903（撤销）关闭；旧 generation 的迟到回调不得影响新会话。

## 新服务端执行边界

`engine` 只提供原生连接、字符串路由、限流、认证状态机与对象结果出口；它不导入游戏域、shared 业务类型、
数字协议号或 Protobuf。`server` 负责：

1. 用 shared codec 解析/序列化外层帧，并对 route req/res/push 调用 shared validator。
2. 用外部身份服务契约认证、复验、原子在线归属和强制下线；不得使用旧加密 hash 或本地伪造身份替代。
3. 以字符串路由装配业务 handler；handler 可复用 Action/ServerTask/Bean 的事务和提交后回调，但不得将
   对象再编码为 Protobuf。
4. 在启动时验证 `ALL_LOBBY_RPC_TYPES` 每项都有唯一 handler、模式与 validator 一致。

现有 `serverNew` 旧 Action 使用的是数字 uid、旧 hash 鉴权、生成的 Protobuf 请求/响应和 `_mod` 自动推送，
与此业务契约不等价。因此它们不能通过“路由映射到数字 protocolId”或“PB 转发层”宣称已迁移；需要逐域完成
真实数据转换、持久化幂等和领域推送后才能接入。

## 验收

- [ ] 目录提供独立 Lobby URL，GameRoom 仍使用原有端点和协议。
- [ ] 客户端原生 transport 完成 auth → ready，并保持 `rpc`、`rpcIdem`、`onPush`、generation 隔离语义。
- [ ] 所有 shared 路由都有唯一真实 handler；请求、响应和推送向量通过。
- [ ] token 无效、错区、过大/二进制/非法帧、版本不兼容、重复认证和未认证 RPC 都稳定拒绝。
- [ ] 幂等写验证实际状态和消耗/奖励；多进程与单进程同一向量行为一致。
- [ ] 活动源码、生成、构建、依赖和调试链无 Protobuf；Bean 兼容记录未重置。
