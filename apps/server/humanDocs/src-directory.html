服务端 src/ 目录构成与关联

面向 Colyseus 游戏服务端的源码导航。按“入口 → 传输 → 领域 → 基础设施 → 数据/玩法”理解最容易。

位置：apps/server/src　·　生成物（如 manifest/catalog/schema generated）由 codegen 维护，勿手改

一、整体请求与生命周期

src/index.ts启动、注册、停服
→
app.config.tsHTTP + Colyseus 配置
→
HTTP / WebSocket / Room三类运行时入口
platform外部身份 HTTP 接缝
↔
core锁、缓存、数据库、幂等
↔
player / kits玩家档与玩法能力
HTTP 适合健康检查、版本、公告和管理/支付回调；Lobby WebSocket 承载一问一答 RPC 与主动推送；GameRoom WebSocket 承载 Schema 状态同步和固定逻辑帧。三条入口共享 core 的一致性原语，并从 @game/shared 读取协议契约。

二、目录树（截至当前源码）

src/
  ├─ index.ts                 服务端启动、路由注册、后台 worker、优雅停服
  ├─ app.config.ts            Express/Colyseus 应用与 transport 配置
  ├─ shutdown.ts              统一停服聚合与有序清理
  ├─ core/                    共享领域基础设施与并发/存储原语
  │  ├─ archive/ auth/ compute/ economy/ guild/ infra/ match/ redeem/ rooms/
  ├─ http/                    HTTP endpoint（按 domain/method 组织）
  ├─ platform/                外部 WebPlatform 身份服务适配
  ├─ player/                  玩家档案、角色状态与修复 worker
  ├─ rooms/                   Colyseus 实时房间、mode、Schema
  │  ├─ core/ modes/ schema/
  ├─ websocket/              Lobby RPC、推送与动态 handler 装载
  └─ kits/                    可组合 kit 的服务端实现（arena、slg）

三、一级目录职责

入口

index.ts / app.config.ts / shutdown.ts

构成进程组合根。index.ts 先注册 Redis/MySQL/WebPlatform 生命周期，再装载 RPC，启动监控、踢人、角色修复和监听端口；异常启动也复用停服清理。

关联：调用 http、websocket、rooms，并协调 framework/infra、player、platform。

基础层

core/

服务端数据与并发原语的统一入口：锁与 fence、幂等、UoW dirty commit、Redis/MySQL、生命周期、错误映射、经济/工会/兑换码、比赛证据和私房邀请。

业务 handler 应优先复用这里，避免绕过锁、事务、outbox、缓存和一致性边界。

传输层

http/

短请求 HTTP endpoint。每个 <domain>/<method>.ts 用 shared contract 创建 endpoint；manifest.generated.ts 是自动生成的静态装配表。

当前域：misc、notice、admin、pay；_support/ 只放复用 helper。

传输层

websocket/

LobbyRoom 上的 RPC 和 push。loader.ts 扫描 domain handler，dispatcher.ts 做路由、限流、校验、超时与错误映射，push.ts 管理在线连接和 mail wake。

与 rooms/ 分工：这里是请求/响应；实时玩法状态在房间。

实时玩法

rooms/

Colyseus GameRoom 运行时。GameRoom.ts 负责认证、准入、生命周期、时钟、消息闸和结算壳；modes/ 提供具体玩法；schema/ 提供同步状态。

玩法登记走生成的 modes/catalog.ts，状态来自 gameplay 单源 codegen。

适配层

platform/

游戏服访问外部 WebPlatform 的唯一入口。webPlatformClient.ts 负责 strict verify、角色登记、超时、重试、熔断和响应校验；devAuthProvider.ts 仅供非生产开发模式。

数据层

player/

玩家角色与档案流程：userStore.ts 读写玩家档，character.ts 保证角色就绪，characterRepair.ts 补偿外部角色登记失败，characterState.ts 和 repair 逻辑承接状态。

组合能力

kits/

可复用的玩法基础能力。arena 提供棋盘仓储与 host，slg 提供地图、行军等服务；插件可通过 kit API 使用能力，kit 自身不替宿主定义通用协议。

四、core 子目录速查

目录作用典型调用方
infra/配置、Redis key/路由/Lua、MySQL、lease、stream consumer、生命周期监控所有入口与领域模块
auth/组 session cache、踢人总线；账号权威仍在 platformLobbyRoom、GameRoom、index
economy/货币、商品、购买、ledger/outbox、relayershop RPC、arenaShop
rooms/私房邀请码与 access ticket Redis 层、私房 RPCGameRoom、room RPC
match/比赛 evidence 的生产、消费、回放校验GameRoom、settle worker
compute/worker_threads 纯 CPU 计算池；大计算不放 handler需要异步计算的领域任务
archive/冷档 freeze/thaw 与容量/用量账本实验模块后台 worker、档案流程
redeem/ / guild/ / arenaShop/兑换码、工会 Demo、arena kit 上的商店插件服务对应 websocket RPC 与后台逻辑

五、典型链路

登录并进入 Lobby

websocket/LobbyRoom.ts → platform/webPlatformClient.ts strict verify → framework/auth/session.ts 缓存组会话 → player/character.ts 确保角色 → websocket/push.ts 注册在线连接。

Lobby RPC

client → LobbyRoom → dispatcher → websocket/<domain>/<method>.ts → core/player/kits → validated reply。路由全集来自 shared descriptor，loader 启动时校验实现与契约完全一致。

实时对局

client → GameRoom.onAuth/onJoin → rooms/core policy → modes/<mode> → schema state。房间壳持有 transport、认证、锁、时钟和生命周期；mode 持有玩法规则，状态 Schema 由 gameplay 单源生成。

写路径一致性

handler/mode 产生业务意图 → core 的锁、fence、幂等、UoW 和事务边界 → MySQL/Redis/outbox；需要跨进程处理时进入 stream consumer 或 worker。

六、修改时的最短路径

  1. 协议、错误码、玩法 manifest 先改 shared 或对应单源。
  2. 按职责选择 http、websocket 或 rooms 入口。
  3. 持久化和并发操作复用 core；外部身份只经 platform。
  4. 玩法专属逻辑放 rooms/modes 或插件/kit，通用房间能力留在 rooms/GameRoom.ts。
  5. 运行相应 codegen，再执行 typecheck、测试和同步校验。
