# AI 开发与验收：在进程外提供可执行工作流

> 目标设计，尚需实现与验收；不是当前仓库的完成清单。返回 [最小框架入口](README.md)。

## AI 最小化体现在哪里

对应 G2，联合验证 G1、G3～G7。目标是让 AI 完成一项功能时只需理解相关契约、模块及验证入口；AI 平台本身不加入线上游戏进程。构建时生成常规接线，保留可读、可追溯的源定义即可，不用生成代码数量证明效率。

| 环节 | 应提供的最小工具能力 | 执行位置 | 应留下的证据 |
|---|---|---|---|
| 找位置 | 模块索引、所有者、真实接口、依赖、手写／生成边界 | 开发机／只读工具 | 引用的源定义及影响模块，避免扫描全部业务 |
| 写功能 | 一个真实可运行的最小 Action／模型／同步示例，固定扩展入口 | 开发机 | 手写差异、契约变更、业务规则和失败语义 |
| 准备环境 | 依赖诊断、隔离存储／端口／账号、正式初始化 | 外部开发启动器 | 成功或阻塞的阶段、缺少条件与可执行下一步 |
| 验证 | 受影响模块的快速检查，随后执行完整验收 | 开发机／CI／测试 worker | 实际命令、退出码、真实存储与客户端结果、未覆盖项 |
| 找问题 | 通过错误码、模块、阶段和关联编号追到提交或任务 | 外部诊断工具；游戏进程输出必要证据 | 可复核原因、固定输入或故障用例、修复后复验 |
| 管理权限 | 环境身份隔离、最小必要授权、敏感操作审计 | 工具与授权服务 | 操作目标、授权范围、差异和验证记录；无凭证泄露 |

以上是待建设的工具契约，不代表新增命令已实现。本仓现有命令见 [AGENTS.md](../../AGENTS.md) 和 [服务端开发说明](../SERVER.md)；实现新工具时须给出实际可执行入口，不用文档中的示意名称伪装成现有能力。

## 真实手写工作量与 AI 效率怎么比较

| 比较项 | 最小框架期望的手写内容 | 实测记录方式 |
|---|---|---|
| 业务规则 | 参数、字段、条件、计算和领域调用 | 相同逻辑、同步行为、失败语义；统计新增／修改的手写有效行与文件数 |
| 公共接线 | 依赖、权限范围、幂等及提交策略声明 | 单独统计声明与重复样板；锁实现、序列化和状态响应不应逐业务复制 |
| 测试 | 正常、越权、资源不足、重复并发、持久化和同步断点 | 测试代码单列，不能为了减少总行数取消必要验证 |
| 生成物 | 不手改，由固定命令派生 | 简述生成是否一致、能否追溯；不混入手写代码节省比例 |
| AI 开发耗时 | 找入口、准备环境、实现、验证、修复 | 固定模型版本、工具权限、冷／热环境，记录首次有效反馈时间及总耗时；token 只报实际可计量值 |
| 人工与质量成本 | 介入次数、原因、返工及漏检问题 | 对同一预设故障检查定位准确性与修复后复验；失败、阻塞与未执行单独标记 |
| 运行最小化 | 默认模块数、运行依赖、启动时间、空闲／负载内存 | 固定版本、数据、机器和负载，比较拆分前后所有相关进程的总资源及游戏进程资源 |

不能仅因文件移到另一个进程，就宣称总内存降低或 AI 更快。先测基线，再用相同条件重复验证；本次仅重组设计文档，没有新增效率或容量实测结论。

## 目标验收矩阵

| 目标 | 最小验证场景 | 通过证据 |
|---|---|---|
| G1 核心最小 | 最小模块清单启动，检查启动依赖，关闭外围控制服务 | 无后台消费／扫描／发布循环被暗中启动；记录依赖、进程和资源 |
| G2 AI 高效 | 固定需求新增功能，定位预设故障并修复 | 可复核手写差异、耗时、介入次数、诊断原因和复验结果 |
| G3 协议与同步 | 共用契约更新、旧客户端兼容、零值／删除／重复／乱序／重连 | 实际客户端与重载存储一致；成功响应未由业务重复拼玩家数据 |
| G4 可恢复 | 提交前、提交后通知前、任务执行中杀进程 | 不重复扣发；结果查证、重载和补交付正确；Redis/MySQL 恢复另有演练 |
| G5 扩缩容 | 同机多进程、跨机、缩容与旧实例恢复 | 路由、任务认领、同步和写入资格正确，容量收益及瓶颈有数值证据 |
| G6 外围可替换 | 断日志接收器、后台、配置发布，再替换一个外围适配实现 | 遥测资源有界、授权与状态语义不变；必要依赖的失败不被误报成成功 |
| G7 生产可维护 | 实际发布／回退、告警触发、隔离备份恢复 | 放行记录、值班处理和恢复后核账，登记环境、恢复时间和数据损失 |

### 28．测试、模拟与质量验收

让正确性可检查，并让 AI 和开发者快速得到可信反馈。

参考方向：保留 gameKit 的契约及故障测试覆盖，吸收 Alloy 的结构检查与模块组织；测试入口按模块统一，补真实最小启动、多进程崩溃恢复、同机及跨机扩容、缩容和滚动替换验收。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 28.01 | 一键测试环境 | 准备隔离数据库、账号和配置，测试结束后可清理，不碰正式数据。 | 基础 |
| 28.02 | 相同验收用例 | 需求先写清输入、输出和错误条件，人与 AI 都按同一标准完成。 | 基础 |
| 28.03 | 规则测试 | 验证数值边界、满级、资源不足和重复请求，不只测正常点击一次。 | 基础 |
| 28.04 | 真实存储测试 | 检查重载后的数据，不用内存假对象替代真正保存成功。 | 基础 |
| 28.05 | 同步和重连测试 | 验证玩家实际收到的状态、零值、删除、乱序和重连快照。 | 基础 |
| 28.06 | 并发与故障测试 | 同时操作、保存失败、进程中断后验证不重复、不丢数据及锁可释放。 | 基础 |
| 28.07 | 真机与性能验收 | 验证微信真机、切后台、弱网和目标容量，不能以本地单测代替。 | 基础 |
| 28.08 | 发布质量闸门 | 编译、接口、数据兼容和关键验收失败时，阻止正式发布。 | 基础 |
| 28.09 | 自动玩家模拟 | 模拟登录、成长和长时间运行，用于发现累积错误和性能退化。 | 运营 |
| 28.10 | 崩溃恢复验收 | 在提交前后、通知前和任务执行中终止业务进程，并测试内存上限退出；重启后检查存档、凭据、补交付和客户端状态，确认不重复扣款发奖。 | 基础 |
| 28.11 | 扩缩容验收 | 实测同机增进程、跨机加实例、缩容和滚动替换，核对请求路由、跨节点同步、任务认领、旧实例写入及资源占用，保存容量与恢复证据。 | 按需 |

### 29．AI 与开发者工作台

让 AI 少猜接口、少漏步骤，也让人工能审查其结果。

参考方向：围绕 Alloy 的模块、Action、Bean/Mod 提供一致的开发与查询入口；吸收 gameKit 的可检查约束和 eerie 的运维经验，补齐最小启动器及局部验证。AI 效率通过固定需求和验收条件的实测评估。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 29.01 | 模块说明与示例 | 给出经过验证的最小业务、存档和同步示例，明确应该改哪些文件。 | 基础 |
| 29.02 | 接口与字段查询 | 快速查找真实可用方法、字段和错误码，避免 AI 编造不存在的 API。 | 基础 |
| 29.03 | 局部验证入口 | 修改一个模块时先跑相关验证，缩短反馈，再执行上线所需的完整检查。 | 基础 |
| 29.04 | 真实最小启动器 | 提供包含正式初始化顺序的测试入口，避免每次都重新猜全局变量和引擎钩子。 | 基础 |
| 29.05 | 权限及环境限制 | AI 的测试权限与正式数据操作分开，敏感操作经过确认和审计。 | 基础 |
| 29.06 | 改动与验收报告 | 列出实际改动、测试命令、失败项和未覆盖风险，不只报告代码行数。 | 基础 |
| 29.07 | 可复现实验 | 比较开发效率时固定需求、模型和验收，保存日志；没有计量的时间或 token 不编造。 | 运营 |
| 29.08 | 自动生成简化 | 由工具补常规接线并检查生成结果，业务开发者只维护确定的源定义。 | 运营 |


## 建设顺序与面向使用者的验收

| 阶段 | 主要模块与范围 | 交付给团队的可见结果 | 完成标准 |
|---|---|---|---|
| A．先跑通一条正确业务链 | 01、02、04～08、21、28、29 的基础部分 | 新玩家登录，消耗服务器持有的材料，进度保存后界面自动更新 | 重复请求不重复扣除、错误不改档、重连和重启后结果一致 |
| B．形成最小上线能力 | 03、22～28 的基础部分，以及 12 的维护公告 | 安全部署、维护、查档、告警、恢复都有明确入口 | 目标容量及真机通过，能回退，能从备份恢复，后台操作可审计 |
| C．按首发玩法补系统 | 09～16、17～20 中实际用到的能力 | 选用的钱包、道具、房间或排行能完成自己的完整业务链 | 不只做好正常路径，也能解释失败、重试、离线和历史数据 |
| D．按商业化需要开放 | 11 支付及其依赖的账本、奖励、可靠交付、客服和权限 | 玩家能购买，客服能查，异常订单有人处理 | 真实平台验签、金额核对、重复回调、补单、退款和对账完成验收 |
| E．提升持续运营效率 | 配置灰度、批量后台、任务看板、模拟玩家和 30 数据分析 | 运维少用临时脚本，问题有证据，调整效果能评估 | 日常操作可追踪，异常处理时间和重复事故率可度量 |
| F．按规模扩展 | 跨服、合服、同机多核与跨机扩容、逐角色扩缩容、存储扩容及复杂风控 | 人数或玩法增长后仍能稳定服务 | 在目标规模验证扩容收益、安全缩容、滚动替换、任务交接、故障切换与跨节点同步 |

阶段 A 将模块、请求、存档、自动同步及安全提交接成完整链路并验收，公共能力使用统一入口。若首发就付费，D 必须提前到上线前；若首发有聊天，内容审核与举报也必须提前。不存在“先上线收钱，再补支付安全”的阶段安排。

## 七、从普通使用者角度验收

| 谁来验收 | 可以直接验证的问题 |
|---|---|
| 玩家体验负责人 | 断网重连后，余额、背包和等级是否正确？按钮失败时有没有明确解释？ |
| 策划 | 配置改动影响哪些玩家？能否先预览、验证，再发布？ |
| 运营 | 能否维护开关、发公告、定向补偿？批量操作能看到进度和影响范围吗？ |
| 客服 | 玩家给出账号或订单号后，能否看到事实记录并说明问题？ |
| 财务或支付负责人 | 每笔付款、到账、发货和退款是否能对应起来？异常订单能否查证并处理？ |
| 值班人员 | 故障有没有通知？该找谁？能否停止故障扩大，并按说明恢复？ |
| 开发者 | 新增一个字段是否要多处复制？新增接口能否及时发现漏登记、漏校验？ |
| AI 开发审查者 | AI 使用的是真实 API 吗？测试是否经过实际存储及同步？是否留下未覆盖项？ |
| 项目负责人 | 首发需要的系统是否闭环？哪些只是设计、哪些已经实现、哪些已有验收证据？ |
