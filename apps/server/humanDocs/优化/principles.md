# 设计原则与八层职责

> 目标设计，尚需实现与验收；不是当前仓库的完成清单。返回 [最小框架入口](README.md)。

## 如何使用原则

[README](README.md) 的七项目标用于快速作设计决策，下列 17 条原则保留更完整的行为和验收约束。模块的“基础”标记不再作为进入核心的理由；先判断是否普遍需要，再决定职责、部署位置和启用条件。运行位置以 README、runtime 和 platform 的新边界为准。

| 总目标 | 对应的既有原则 |
|---|---|
| G1 核心最小化 | 模块拥有职责；状态、计算与提交分开；按职责拆分进程；公共保护默认接入 |
| G2 AI 高效开发 | AI 可理解／开发／验证／定位；单一源定义；操作结果可追踪；以证据验收 |
| G3 业务简单、双端一致 | 单一源定义；先提交再自动同步；普通业务与房间分别建模 |
| G4 状态可靠、进程可恢复 | 状态外置；进程可恢复；一个权威来源；幂等；先正确再优化 |
| G5 多进程可扩缩容 | 按职责拆进程；故障有边界；扩缩容不改变语义 |
| G6 外围可替换 | 正式接口协作；故障有边界；公共安全保护；操作结果可追踪 |
| G7 可生产验收 | 以证据验收；结果可追踪；先正确再优化；进程及状态恢复 |

## 完整原则与推导方法

**进程负责计算，存储提供已提交状态的依据，模块承担明确职责，框架提供公共保护，客户端按约定同步状态。** 这句话针对普通持久业务；实时房间临时状态与预测显示遵守各自明确的边界。

以下 17 条原则是目标框架的设计基线，不是现有实现的能力声明。原蓝图的 30 个模块和 251 项子功能应逐项由原则解释其必要性；选择 Alloy、gameKit 或 eerie-server 的方案时，先检查它是否满足原则，再比较开发、运行和维护成本。原则不替代本仓当前契约，也不代表已经授权替换运行时、网络库或数据层。

| 原则 | 通俗说明 | 设计约束 | 适用边界 | 验收标准 | 对应模块 |
|---|---|---|---|---|---|
| 关键业务状态不依赖进程内存 | 玩家进度不能因为某个业务进程退出就消失，重启后应能找回已提交状态。 | 普通玩法热档主要存 Redis，货币、订单及交付凭据按职责存 MySQL；本地对象和缓存可重新加载，不承担唯一持久依据。 | 执行请求仍会使用内存；Redis 本身也是内存数据库，需持久化与备份。实时房间临时状态另定恢复规则。 | 终止业务进程后由新实例读取已提交存档；核对余额、进度和未完成任务，不能依靠旧进程对象恢复。 | 玩家存档与数据模型；多进程架构、基础设施与扩缩容；备份、恢复与数据修复 |
| 普通业务进程可替换、可恢复 | 进程发生异常后可以重新启动或由其他实例接手，减少人工修档和长时间停服。 | 启动时完成配置、依赖及就绪检查；在途操作有凭据可查，任务可重新认领，客户端可重连；连续崩溃应限速并告警。 | 不承诺所有进程都能无损重启。共享存储、整机故障、未保存的房间状态以及持续触发的程序缺陷需独立处理。 | 在提交前、提交后和通知前终止进程，验证重启就绪、操作查证、任务续接及客户端补齐，并记录恢复时间。 | 构建、部署、发布与回退；可靠队列与跨模块交付；测试、模拟与质量验收 |
| 进程按职责拆分并独立扩缩容 | 连接多就扩入口，任务积压就扩消费者，计算忙就扩计算资源，不必整套服务器一起扩大。 | 明确网关、普通业务、后台任务、重计算和房间角色；提供各自启停、健康检查、容量上限、路由及安全缩容入口。 | 模块不等于独立进程，连接入口与普通业务初期可合并；启用的后台消费、重计算及外围系统按运行职责独立；线程池不等于独立进程隔离。单例任务不能简单复制，自动扩缩容可后续建设。 | 同机增加进程、跨机增加实例并缩容，验证工作分配、任务交接、资源使用与实际容量收益。 | 应用组装与模块管理；重计算与资源调度；多进程架构、基础设施与扩缩容 |
| 状态、计算与提交职责分开 | 规则计算负责算出结果，存储负责记住结果，统一提交负责让一次修改按约定生效。 | 业务通过正式模型或领域接口加载数据，在受保护的状态上检查和计算，再按存储边界提交；纯计算不直接发奖或调用外部支付。 | 分离是职责边界，不要求每层单独部署。计算仍可临时修改工作对象，但不能把尚未提交的对象当作最终结果。 | 固定输入可重复验证计算；保存失败时不报告成功，重算不会直接重复产生奖励等外部效果。 | 通用玩法开发能力；玩家存档与数据模型；安全提交与防重复执行；重计算与资源调度 |
| 每类数据只有一个权威来源 | 余额、订单、玩家档案各自有明确的最终依据，发生差异时知道该以哪一份为准。 | 声明每类数据的所有者、权威存储和写入口；缓存、客户端显示及分析报表均从权威结果派生，不能各自记一份真账。 | 一个来源不等于一台数据库或没有副本；副本与冷档切换必须有明确的归属、版本和恢复协议。 | 制造缓存过期、客户端旧状态及双存冲突，验证系统按权威规则读取、拒绝不明覆盖并可解释差异。 | 玩家存档与数据模型；钱包、货币与经济账本；备份、恢复与数据修复；数据分析与经营报表 |
| 重要写操作重试不重复产生业务效果 | 重复点击、网络重试或任务重新执行，不应多扣一次钱或多发一次奖励。 | 购买、领取、结算等使用稳定操作编号、请求内容绑定和可查结果凭据；重试沿用原标识，新业务操作才使用新标识。 | 不是把任何代码重跑都变安全，也不承诺消息只投递一次；需规定凭据保留期和过期重试策略，外部系统另做去重或补偿。 | 并发重复请求、相同编号换参数、提交后崩溃及任务重放时，结果唯一且可查，过期请求按明确规则处理。 | 安全提交与防重复执行；商城、订单与支付；钱包、货币与经济账本；可靠队列与跨模块交付 |
| 先提交，再发布成功状态并自动同步 | 客户端看到已完成时，应有保存成功的依据；玩家数据变化由框架同步，业务不用每个接口重复拼角色数据。 | 从已提交变更生成快照或增量；业务响应只携带本次确认、订单号或独有结果。跨系统未完成明确标为处理中，重连可补齐。 | 接收确认不等于业务完成。临时对局状态和客户端预测需明确标记，不能作为已保存资产；同步可附在响应或单独推送中。 | 保存失败不推送成功状态；提交成功但通知丢失时，客户端补齐后与存储一致，并覆盖零值、删除、重复及乱序消息。 | 协议与版本契约；安全提交与防重复执行；客户端状态自动同步；客户端接入、界面与资源 |
| 普通业务与实时房间分别建模 | 养成、背包和商城使用请求及持久状态；实时对局使用房间和局内状态，各自解决适合的问题。 | 局外采用 Action 与 Bean/Mod 风格组织，房间按需使用 Colyseus；共用身份与正式结算入口，每个字段只有明确归属。 | 房间允许临时状态驻留内存。崩溃续局、快照、重放或中断补偿需要单独建设，不能把进程重启当作自动续局。 | 同一账号在局外与房间中的状态边界明确；掉线及房间中断后按规则处理，同一结算不重复改变永久资产。 | 网络连接与请求入口；玩家存档与数据模型；客户端状态自动同步；实时房间与对局 |
| 模块拥有职责，通过正式接口协作 | 钱包管记账，道具管物品，玩法管规则；新功能可以按清晰入口接入和维护。 | 模块集中声明依赖、协议和扩展点；其他模块经正式领域接口操作其数据。持久化实现由所属模块或基础层封装，后台也走同一写入口。 | 不禁止数据所有者实现必要存储代码，也不要求每个模块独立部署；模块间调用不自动构成跨库事务。 | 新增功能可沿登记点接入；检查越界写入、循环依赖及旁路后台操作，移除模块前能识别依赖和数据处理责任。 | 应用组装与模块管理；通用玩法开发能力；钱包、货币与经济账本；运营、客服与管理后台 |
| 公共安全保护默认接入，业务规则显式声明 | 开发者少重复写锁、校验和异常清理，同时明确声明资格、额度和数据可见范围。 | 统一入口提供身份、参数、权限、写入保护、错误处理和资源收尾；模块声明保护范围、幂等策略与业务条件，缺少必需接线时检查失败。 | 框架不能自动推断所有业务规则；只读、资产修改和纯计算适用不同保护，不要求每条请求都加分布式锁。 | 新增最小业务无需复制公共安全代码；遗漏必需配置可被检查发现，越权、并发及异常路径均有验证。 | 网络连接与请求入口；协议与版本契约；安全提交与防重复执行；权限、安全与隐私 |
| 故障有边界，资源有上限 | 一个任务或实例异常时，尽量只影响局部，不让排队、连接或内存无限增长拖垮全服。 | 独立进程配 CPU、内存、队列和连接预算；依赖超时与重试有上限，支持降载、健康剔除及失败任务接手。 | 同机资源耗尽、共享 Redis/MySQL 或网络故障仍可能影响多个实例；隔离不能消除共同依赖和容量瓶颈。 | 注入计算卡死、内存超限及依赖超时，测量其他实例影响范围；验证限流、告警、恢复和积压不会无限增长。 | 重计算与资源调度；日志、监控、告警与值班；构建、部署、发布与回退；多进程架构、基础设施与扩缩容 |
| 扩容与缩容不改变业务语义 | 增加进程或机器后，玩家权益、并发写入和任务结果应与单实例时一致。 | 统一服务发现、路由、共享写保护、幂等、任务认领和跨节点通知；退出实例先排空或交接，再撤销其处理资格。 | 多实例不保证吞吐线性增长；热点数据、锁和数据库可能限制扩容。连接及房间迁移需独立方案，不能默认无缝移动。 | 用同一业务用例比较单实例、多实例、跨机及缩容结果，验证不重扣、不漏交付、状态正确，并报告容量瓶颈。 | 安全提交与防重复执行；可靠队列与跨模块交付；多进程架构、基础设施与扩缩容；测试、模拟与质量验收 |
| 单一源定义，自动生成可追溯 | 协议、字段和模块登记有清楚的真源，工具承担重复接线，人与 AI 都能查到真实接口。 | 派生文件通过固定命令生成并检查；业务规则保留可读源代码，协议与字段变更进行兼容校验，不手改生成物。 | 生成不能替代业务判断与测试，也不能隐藏额外状态来源；使用转换器或生成器时，测试和构建必须使用相同正式链路。 | 修改一处源定义可重复生成一致产物；发现遗漏接线或不兼容变更，能追溯生成内容并用正式编译链验证。 | 应用组装与模块管理；协议与版本契约；玩家存档与数据模型；AI 与开发者工作台 |
| 操作结果可解释、可查询、可追踪 | 玩家知道操作是否成功，客服能查证，开发者能定位；超时不能被简单当作失败重做。 | 区分已接收、处理中、已完成、已失败及结果待查；用稳定错误码、操作编号和必要审计串联请求、保存与交付。 | 只保留必要信息，凭证和敏感数据不得泄漏到客户端或日志；高频临时消息不要求逐条永久审计，关键权益操作要留据。 | 遇到超时或交付延迟时，按操作编号能查到事实和下一步；日志可关联但无敏感泄漏，客服结论有依据。 | 协议与版本契约；商城、订单与支付；运营、客服与管理后台；日志、监控、告警与值班 |
| 先满足正确性约束，再用测量优化效率 | 框架首先保护玩家权益，再通过缓存、并行或批量提升性能；同时重视开发反馈速度和维护成本。 | 定义必须保持的余额、状态及交付规则，先测瓶颈再优化；缓存可重建，并行有保护，失败降级不能绕过提交与权限。 | 不要求所有工作强一致或同步完成；统计等可接受延迟，跨系统可最终一致，但处理中状态和最终收敛条件必须清楚。 | 优化前后运行同一正确性、故障及容量用例，同时报告吞吐、延迟、资源和开发成本变化，不以省码替代保障。 | 安全提交与防重复执行；钱包、货币与经济账本；多进程架构、基础设施与扩缩容；AI 与开发者工作台 |
| 生产能力以可复核证据验收 | 有代码、可启动或理论上支持，不等于已经能承载正式玩家。 | 每项能力明确适用范围、失败行为、验收环境和放行条件；保留测试、真实存储、客户端联调、恢复演练及容量结果。 | 单测不能代替真机、弱网或容灾；一套规模下通过不代表任何规模都通过。记录未覆盖范围，不编造效率、稳定性或工期。 | 原则能映射到模块和验收用例；上线所需检查失败时阻止发布，恢复时间、数据损失和容量指标有对应实测记录。 | 测试、模拟与质量验收；备份、恢复与数据修复；构建、部署、发布与回退；AI 与开发者工作台 |
| AI 与开发者可高效理解、开发、验证和定位问题 | 让 AI 和开发者通过统一、可查询、可执行的入口理解框架、实现功能、验证结果并定位故障，减少隐式知识、人工接线和反复猜测。 | 结构清晰、接口可查：目录职责、真实 API 和生成物边界明确；标准入口、示例可运行：沿正式扩展点开发；环境可启动、验证可执行：提供隔离启动、局部验证和完整验收入口；错误可定位、故障可复现：错误含模块、阶段及必要关联信息，测试输入可固定；权限明确、过程可追溯：操作受控，保留改动和验证证据。 | 这是贯穿各层的设计目标，不仅是 AI 工作台功能；不承诺 AI 永不出错、零人工介入或任意环境一键可用。缺配置、权限或依赖时应给出可执行诊断，效率不能以绕过权限、减少必要验收或泄漏数据换取；已有生成、追踪及证据原则继续负责具体约束。 | 固定需求、模型、工具权限、依赖条件和预设故障，从干净的隔离环境完成新增小功能、运行验证、定位故障并修复后复验；记录首次有效验证耗时、总耗时、人工介入次数、定位结果和覆盖范围，与约定基线比较，未测时间或 token 不编造。 | 应用组装与模块管理；协议与版本契约；日志、监控、告警与值班；权限、安全与隐私；测试、模拟与质量验收；AI 与开发者工作台（牵头，各层共同落实） |

### 第 17 条原则的五项子要求

这是一条框架级总原则，下面五项是它的子要求，不另计原则数量。它与“单一源定义，自动生成可追溯”“操作结果可解释、可查询、可追踪”“生产能力以可复核证据验收”等原则配合，具体安全及正确性要求仍遵守原原则。

| 子要求 | 框架应提供什么 | 如何判断有效 |
|---|---|---|
| 结构清晰、接口可查 | 一致的目录、职责与命名，真实接口、字段、错误码和依赖查询入口；明确手写源和生成物，文档随契约更新 | AI 和开发者能依据仓库信息找到修改位置、真实调用方式和必要约束，减少猜接口或反复询问内部约定 |
| 标准入口、示例可运行 | 经过验证的最小业务、数据与同步示例；标准扩展点和可重复生成流程；缺少必需声明时明确报错 | 新功能沿正式开发路径完成，不复制公共接线，不依赖脱离正式初始化或编译链的假示例 |
| 环境可启动、验证可执行 | 在依赖条件明确后，以统一命令启动隔离环境；提供快速局部验证和完整验收；错误说明缺少的条件及下一步 | 能独立启动并获得有效反馈；区分环境故障和业务失败，报告成功、失败、未执行及未覆盖项目 |
| 错误可定位、故障可复现 | 错误含模块、阶段、稳定错误码及必要关联标识；日志脱敏；支持固定时间、随机输入和测试账号，以及可控故障注入 | 对预设故障能给出可复核原因，形成失败用例并验证修复；不只让示例正常跑通一次 |
| 权限明确、过程可追溯 | 默认开发测试环境、最小必要权限、敏感操作确认与审计；保留变更差异、实际命令、测试结果及限制 | 能审查做了什么、为什么改、如何验证；未授权操作受到阻止，证据中不泄漏凭证或敏感数据 |

验收使用固定需求、模型及工具条件，从干净的隔离环境依次完成“新增小功能 → 执行验证 → 定位预设故障 → 修复并复验”。先记录当前基线，再评估首次有效反馈时间、总耗时、人工介入次数、定位准确性及验证覆盖；本原则不预填未经测量的效率提升，也不以减少安全检查换取更快完成。


### 最终框架按以下八层设计

分层表达代码与能力的职责，进程划分表达运行和故障隔离的方式，两者不是一一对应关系。一层可以被多个进程使用，一个进程也可以装配多层；连接入口与普通业务可按实际负载合并；外围系统、后台消费与重计算按运行职责独立，不能仅因为有八层就要求八个独立服务。安全、协议、可观测和验证规则贯穿各层。AI 与开发者的高效理解、开发、验证及排障也由各层共同保障：每层提供清晰契约、可执行入口和必要诊断，AI 工作台统一汇集这些能力。

| 层次 | 主要职责 | 职责边界 | 主要依据的原则 | 对应模块 |
|---|---|---|---|---|
| 接入层 | 登录与身份接入、连接管理、请求配对、路由、限流及协议参数校验 | 接收请求并交给正式业务入口；不绕过领域能力直接扣款或改玩家档案 | 公共安全保护默认接入；操作结果可解释；扩缩容不改变语义 | 02 账号、03 区服、04 网络、05 协议、23 权限 |
| 业务层 | 组织养成、商城、任务、公会等业务流程，检查业务资格并调用规则计算 | 明确这次操作要做什么，通过领域和模型接口执行；不重复实现底层锁、SQL、Redis 命令或同步接线 | 模块拥有职责；状态、计算与提交分开；单一源定义 | 10 道具、11 商城、12 邮件、13 玩法、14 房间规则、15 排行、16 社交、20 活动 |
| 领域能力层 | 提供钱包、奖励、条件、权限、并发保护、幂等和提交协调等统一能力 | 数据所有者提供正式写入口；公共机制由基础设施适配支撑，不把具体角色数值或活动规则硬编码进通用机制 | 一个权威来源；重要写操作重试不重复；公共安全保护默认接入 | 07 安全提交、09 钱包及各业务模块的领域服务、23 权限 |
| 状态层 | 数据模型、变更追踪、存储读写、版本和迁移；承接 Redis 热档、MySQL 账本等权威数据及可重建缓存 | 封装加载和持久化机制，不自行决定购买资格等业务流程；内存工作对象不等于已提交结果，跨存储写入不能伪装为一个本地事务 | 关键状态外置；状态、计算与提交分开；一个权威来源 | 06 存档、07 提交的存储适配、09 账本存储、26 存储设施、27 冷档与迁移 |
| 可靠任务层 | 持久任务登记、outbox、消费认领、确认、重试、死信、补偿及受控重放 | 与权威提交协调登记必须完成的后续动作；业务流程由对应模块执行，不把所有同步请求都改成异步任务 | 重要写操作重试不重复；进程可恢复；扩缩容不改变语义 | 17 定时任务、18 可靠交付、19 计算任务接线 |
| 进程运行层 | 按角色装配模块，负责启动、就绪、服务发现、通信、资源限额、排空、托管重启和扩缩容 | 管理谁在何处执行，不定义具体玩法；线程、进程、主机和共享存储的故障边界分别处理 | 按职责拆进程；进程可替换；故障有边界；扩缩容不改变语义 | 01 组装、03 区服路由、14 房间运行、19 计算资源、25 启停发布、26 多进程设施 |
| 客户端同步层 | 按权限从已提交变化生成首次快照和增量，支持连接路由、重连补齐、客户端模型更新及页面订阅 | 业务响应只提供本次操作独有结果；状态载荷由框架派生。房间临时状态走明确的专用同步规则，不覆盖永久档案 | 先提交再自动同步；普通业务与房间分别建模；一个权威来源 | 05 状态协议、08 自动同步、14 房间同步、21 客户端接入 |
| 运维验证层 | 运营与客服工具、日志指标、告警、配置发布、备份恢复、数据修复、压测、故障演练及开发验证 | 后台写入同样经过正式权限和领域入口；不能靠直接改库绕过并发、幂等和账本规则，测试通过范围需可复核 | 操作结果可追踪；公共安全保护默认接入；以证据验收；先正确再优化 | 20 配置、22 后台、23 审计、24 监控、25 发布、27 恢复、28 测试、29 AI 工作台、30 分析 |

模块是“谁负责”，层次是“负责哪类工作”。例如商城模块拥有自己的业务流程，使用钱包领域接口扣款，经过状态层提交，并通过可靠任务层交付、客户端同步层显示结果；它不需要把所有代码都堆在同一层。模块可以在内部区分业务、领域和存储实现，公共接口保持明确。

### 各层怎样完成一次普通操作

| 顺序 | 负责层 | 应发生的行为 |
|---|---|---|
| 1．接收请求 | 接入层 | 确认身份、区服、请求格式和频率，识别本次操作编号 |
| 2．进入受保护的业务入口 | 业务层＋领域能力层 | 确认权限与幂等策略，按修改对象建立锁、事务或版本条件；不能先用无保护的旧数据作最终决定 |
| 3．加载、校验与计算 | 状态层＋业务层＋领域能力层 | 在保护范围内加载状态，检查资源和资格，计算变更；必要重计算交给独立计算资源，提交前按需要重验 |
| 4．提交并登记必要交付 | 领域能力层＋状态层＋可靠任务层 | 只涉及一种存储时按其原子边界提交；需要跨存储交付时，与权威结果一起保存可重试的交付凭据，不能提交后再尝试补写任务 |
| 5．继续交付并表达结果 | 可靠任务层＋领域能力层 | 已完整生效的操作可确认完成；尚未交付完的明确为处理中，消费者按同一凭据重试收敛 |
| 6．同步和显示 | 客户端同步层 | 同步已提交状态，响应说明本次操作；客户端按版本更新模型与界面，断线后补齐而不重新购买 |
| 全程保障 | 进程运行层＋运维验证层 | 提供实例调度、资源限制、关联记录、告警及验收证据，故障后按约定重建或接手 |

普通业务进程退出时，由进程运行层拉起或调度替代实例；状态层重新加载已提交数据，领域能力层查证操作结果，可靠任务层接续未完成交付，客户端同步层处理重连补齐。实时房间未持久化状态、整机和 Redis/MySQL 故障继续遵守各自独立恢复方案。

### 用原则推导设计的顺序

| 顺序 | 要确定什么 | 必须形成的结果 |
|---|---|---|
| 1．明确目标与不变量 | 玩家权益、状态归属、恢复目标和可接受延迟 | 例如同一订单只能发货一次，已提交档案可重载；说明目标规模与未覆盖范围 |
| 2．划分职责与数据权威 | 谁负责规则、谁拥有数据、谁可以写 | 模块边界、权威存储、正式写入口；不能让多个模块各记一份真账 |
| 3．设计提交及失败流程 | 并发、重复请求、保存失败、结果未知时如何处理 | 写入保护、操作凭据、提交边界、必要的可靠交付和补偿；不能先把资产扣完再随意入队 |
| 4．确定同步与对外语义 | 何时可告知成功，何时只能告知处理中 | 已提交状态自动同步，响应说明本次操作；重连、重复与乱序有统一处理 |
| 5．确定进程与扩缩容方式 | 哪些职责要独立运行，怎样分配、隔离和交接工作 | 进程角色、路由、资源限额、单例或并行消费规则、崩溃恢复与安全退出 |
| 6．比较实现与成本 | 哪个参考机制满足原则，哪些地方需要补齐 | 有依据的方案选择与取舍；不以框架名、代码行数或理论性能代替验证 |
| 7．用同一标准验收 | 单实例、多实例、失败及恢复时是否保持约定 | 行为测试、真实存储及客户端验证、故障恢复和容量证据，登记未覆盖项 |

### 每个模块设计前必须回答的问题

| 必答问题 | 写到什么程度才算清楚 |
|---|---|
| 遵守哪些原则，解决什么问题？ | 对应原则名称、责任模块、玩家或团队得到的结果 |
| 数据由谁拥有、最终存在哪里？ | 区分 Redis 热档、MySQL 权威记录、缓存及房间临时状态；明确写入口与数据范围 |
| 一次操作何时算完成？ | 在保护范围内读取、检查、计算和提交；跨存储后续动作在权威事务内登记，未完成时显示处理中 |
| 重试与并发会发生什么？ | 操作标识、参数绑定、锁或版本条件、重复结果和凭据过期策略；锁的范围覆盖被修改的数据 |
| 进程或依赖故障后如何恢复？ | 区分未提交、已提交未通知和交付未完成；写清重载、查证、认领、补偿及存储恢复责任 |
| 多进程、跨机器和缩容时是否保持相同结果？ | 路由、通知、任务分配和旧实例写入资格有规则；容量收益及瓶颈要实测 |
| 如何证明正确且可以上线？ | 明确验收输入、预期结果、真实环境、失败用例和放行条件，不用“已支持”代替证据 |

原则冲突时，先守住玩家权益、权限和已声明的数据语义，再在满足约束的方案中比较成本；只读查询、分析统计和资产交易可以选择不同的一致性与性能策略，但必须明确适用范围。若要改变已确认的原则，应单独说明原因、影响和验收变化，不能在某个模块里悄悄绕过。

## 易混淆边界

| 容易混淆的事情 | 统一规则 | 为什么 |
|---|---|---|
| 业务进程内存与权威数据 | 请求对象可在内存计算，关键已提交状态保存在 Redis/MySQL；实时房间的临时状态单独设计恢复 | 进程替换不应丢失已提交档案，但不能承诺未保存对局可直接续局 |
| 增加进程与增加吞吐 | 按职责扩容并测量路由、锁、存储和连接池瓶颈；单例任务不能复制执行 | 避免多进程重复处理或把共享存储压垮 |
| 进程重启与存储容灾 | 分别验收业务进程、主机和 Redis/MySQL 故障，明确恢复时间及数据损失边界 | 自动拉起业务进程不能修复存储损坏或整机资源耗尽 |
| 多套模块提供同一公共能力 | 公共能力保持一套正式入口，各模块按明确职责接入 | 降低重复接线、维护和 AI 理解成本 |
| 钱包与背包都能改金币 | 每种资产只有一个最终记账来源，其他模块调用它 | 避免两份余额互相覆盖 |
| 自动保存与自动同步 | 变更先通过正式提交，再发可确认的成功状态；尚未完成的跨系统操作标记处理中 | 避免界面显示成功但数据没存住 |
| 请求重试与重新购买 | 同一次操作沿用原标识；新操作必须明确重新发起 | 避免断网自动多买一次 |
| 通知与可靠任务 | “提醒有邮件”允许补查；“发放已付款商品”必须可恢复处理 | 两者不能使用同一种随时可丢消息策略 |
| 计算与奖励 | 计算可以重做，正式发奖必须经过唯一交付凭据 | 避免计算重试造成多次奖励 |
| 管理后台与业务入口 | 后台也调用正式账户、奖励及修复入口，受权限和审计约束 | 避免后台绕过余额守卫或重复发放 |
| 运营报表与真实余额 | 报表用于分析，订单与账本用于确认权益 | 统计延迟不能影响玩家资产 |
| 游戏区服与物理机器 | 角色属于哪个区服和服务运行在哪台机器分开记录 | 迁移机器不应变成迁移玩家身份 |
| 普通请求与实时房间 | 普通请求采用 Alloy 风格的连接与 Action 组织；按需引入 Colyseus 房间，统一身份并明确状态归属 | 避免只因引入房间就重做全部养成接口 |
| 房间状态与永久存档 | 局内临时状态与局外长期数据分开；结束时有明确结算 | 服务器重启后不能把未确认结果当奖励依据 |
| 代码回退与数据回退 | 单独检查数据是否兼容，已发生的支付和领取不能凭代码版本撤回 | 避免回退后重复发奖或遗漏订单 |
| 引擎通用能力与具体玩法 | 框架提供条件、提交、同步等工具；角色职业和副本规则归业务模块 | 避免每款游戏都被迫继承同一套玩法 |
| 实测通过与上线完成 | 只承认实际覆盖的环境、故障和网络范围 | 局部测试通过不能代表容灾及真机已通过 |

## 常见术语

| 术语 | 通俗解释 |
|---|---|
| 模块 | 一组职责相近的功能，例如钱包；不是必须单独部署的一台服务器 |
| 协议 | 客户端和服务器约定好的一张表：能发什么、字段是什么、结果怎么解释 |
| Bean/数据模型 | 用统一方式描述数据字段，让程序更容易读写和追踪变化 |
| Mod/差分同步 | 把玩家数据分组，变化后发送需要更新的部分 |
| 事务/UoW | 一次业务修改的统一处理与提交边界；不能自动保证所有外部系统都能一起回滚 |
| 幂等 | 同一次操作重复到达时，不重复造成扣款或发奖 |
| revision/fence | 用版本或写入资格编号阻止迟到的旧操作覆盖新数据 |
| outbox | 与业务结果一起保存的“待交付清单”，后台按清单补齐后续动作 |
| 死信 | 自动重试仍失败、需要调查或人工处理的任务，不是可以随便删除的垃圾 |
| 冷档 | 长期不活跃的数据放到更低成本的存储，使用前按规则恢复 |
| ACK | 确认收到了或完成了哪次操作；“收到”和“已完成”必须定义清楚 |
| 灰度发布 | 先给少量实例或玩家使用新版本，观察正常后再扩大 |
| drain/排空 | 停止接新任务，等待正在处理的工作收尾后再停服 |
| SLO | 团队承诺并持续衡量的服务目标，例如响应时间和可用程度 |
| RPO/RTO | 故障时最多能接受丢多久的数据，以及希望多久恢复服务 |
