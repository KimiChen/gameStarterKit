# 最小核心：处理一次业务所需的公共能力

> 目标设计，尚需实现与验收；不是当前仓库的完成清单。返回 [最小框架入口](README.md)。

## 纳入核心的判据

同时满足三个条件才进入默认运行核心：普通请求普遍需要；必须在执行或提交边界内保证；移到外部会使正确性依赖一次额外的不可靠调用。可替换存储与网络通过适配器接入；需要可靠交付时才启用登记适配器，消费循环始终独立。

| 对应目标 | 核心职责 | 具体边界 |
|---|---|---|
| G1、G2 模块最小与易开发 | 每个模块声明职责、依赖、契约、所需角色和资源 | 业务只依赖公开接口；构建／启动检查拒绝后台、监控平台、测试器或未选业务进入默认启动依赖；元数据查询不实例化模块 |
| G3 双端一致 | 客户端和服务端共享同一份协议源 | 请求、响应、同步结构、消息名和对外错误码直接共享或统一生成；服务端私有字段和数据库结构不作为公共协议；类型不能替代运行时校验 |
| G4 正确保存 | 数据所有者、保护范围、提交及结果凭据明确 | 在保护内读取再判断；跨玩家／公会修改声明共同保护范围，单玩家锁不是全局一致性保障 |
| G3、G4 自动同步 | 已提交状态按权限映射给客户端 | 临时修改不发布成功状态；普通响应只返回该次操作的确认、标识或独有结果；乱序和丢消息靠版本、重取快照恢复 |
| G5、G6 生命周期 | 初始化、就绪、排空、资源释放及薄诊断接口 | 不启动监控看板、发布控制器或后台调度；初期允许连接适配器与业务合并运行 |

## 一次普通请求的固定路径

| 步骤 | 框架承担 | 业务手写 |
|---|---|---|
| 定义 | 校验协议登记、字段权限和模块依赖 | 请求独有参数、数据字段、所需依赖和业务保护策略 |
| 准入 | 认证、参数校验、限流、错误转换和请求关联 | 谁可执行、需要满足什么条件 |
| 执行 | 建立锁／版本条件，按需加载当前状态，提供工作对象与变更追踪 | 在受保护状态上检查资格、调用公式与领域接口 |
| 提交 | 按存储原子边界保存结果和去重依据；需要时同时登记交付凭据 | 声明此次要提交的业务变化，跨系统未结束时说明处理中 |
| 同步 | 从已提交版本生成授权变化；按连接路由交付并支持重连补齐 | 只返回本次独有结果，不拼玩家完整数据 |
| 收尾 | 释放锁、连接和工作对象，输出有界诊断 | 声明领域错误和必要业务事实 |

单库事务、Redis 原子写和跨存储最终交付是不同能力。框架不能承诺“把任何多库修改放进一个函数就全部原子成功”。同一操作重试沿用原操作编号并绑定参数，结果未知时先查证。

时钟读取、配置快照、权限判定、诊断输出和就绪接口虽然在其他责任模块中有详细说明，仍是必要的薄适配能力；对应关系见 [catalog.md](catalog.md)，不能因为明细移出本文就删掉进程内保障。

### 01．应用组装与模块管理

让新功能接入统一规则，不用每加一个功能就改动整套服务器。

参考方向：采用 Alloy 的模块声明与生命周期，吸收 gameKit 的自动检查，形成一套登记入口。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 01.01 | 模块登记 | 给每个功能登记名字、负责人和使用范围，便于查找及维护。 | 基础 |
| 01.02 | 依赖检查 | 例如商城依赖道具和钱包；启动前检查是否缺少依赖，避免运行一半才报错。 | 基础 |
| 01.03 | 启动和停止顺序 | 先准备数据服务，再开放玩家入口；停服时按相反顺序收尾。 | 基础 |
| 01.04 | 统一扩展位置 | 新功能可登记自己的接口、定时工作、后台页面和日志，不需要另造一套接入方式。 | 基础 |
| 01.05 | 功能开关 | 临时关闭出问题的功能，其他功能继续服务；关闭购买时也要处理已经付款的订单。 | 基础 |
| 01.06 | 模块版本与兼容 | 记录某模块支持哪些数据和接口版本，避免新模块配上旧数据后出错。 | 运营 |
| 01.07 | 可选模块安装 | 按游戏选择支付、排行或公会等模块；移除模块前检查依赖和历史数据如何处理。 | 扩展 |

<a id="m04"></a>

### 04．网络连接与请求入口

让玩家操作稳定到达服务器，断网时也有明确反馈。

参考方向：普通业务连接与请求入口参考 Alloy 的 HTTP/WS 同端口、连接管理和 Action 分发。已核对其心跳及认证超时、包体限制、请求响应配对、健康检查和关闭连接处理；这些能力适合作为入口基础。补齐请求限流、慢连接积压控制、并发执行接线及停服排空验证。Colyseus 留给第 14 模块的实时房间需求，不作为普通养成请求的默认选型。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 04.01 | 加密连接 | 保护登录和操作数据在传输过程中不被轻易窃取或篡改。 | 基础 |
| 04.02 | 连接状态检测 | 识别真正在线、短暂掉线和已断开的连接，及时释放资源。 | 基础 |
| 04.03 | 断线重连 | 网络恢复后重新确认身份和状态，不把每个未完成操作都盲目重做。 | 基础 |
| 04.04 | 请求配对 | 把每条响应对应到正确操作，避免购买结果显示到另一个操作上。 | 基础 |
| 04.05 | 频率和大小限制 | 限制连接数、请求频率与包体大小，防止误操作或恶意请求拖垮服务。 | 基础 |
| 04.06 | 超时与重试反馈 | 区分失败、正在处理和结果未知；超时后先查结果，再决定是否重试。 | 基础 |
| 04.07 | 拥塞与慢客户端处理 | 客户端接收太慢时合并可丢弃的状态更新，保留关键结果并限制积压。 | 运营 |
| 04.08 | 外部接口入口 | 为登录、支付通知和后台查询提供必要的网页接口，使用同样的身份与校验规则。 | 按需 |

<a id="m05"></a>

### 05．协议与版本契约

让客户端和服务器对字段、错误及操作含义理解一致。

参考方向：参考 Alloy 的协议组织、编解码与兼容检查，吸收 gameKit 的单源契约及共享公式原则。每种契约只维护一个真源，工具负责派生，避免维护两份同义协议。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 05.01 | 客户端与服务端共用协议定义 | 请求、响应、状态同步结构、消息标识和对外错误码只维护一份源定义；双端直接共享或由同一份定义生成代码，不分别手写两套。共享内容不含服务端私有模型，仍需运行时校验和旧客户端兼容检查。 | 基础 |
| 05.02 | 参数合法性检查 | 检查数量范围、字段格式和必填项，不能把“类型看起来正确”当作数据可信。 | 基础 |
| 05.03 | 统一错误码 | 用稳定的错误编号区分材料不足、维护中和网络异常，方便界面提示。 | 基础 |
| 05.04 | 自动检查漏接接口 | 接口已声明但没有实现，或实现未登记，检查时立即提示。 | 基础 |
| 05.05 | 新旧客户端兼容 | 增加字段时保证旧客户端可用；无法兼容时明确要求升级。 | 运营 |
| 05.06 | 状态与结果分开 | 角色数据走统一状态同步；业务响应只给确认、订单号或该次操作独有结果。 | 基础 |
| 05.07 | 编码适配 | 按消息类型选择合适的传输格式，开发者不需要为每个功能手写序列化代码。 | 运营 |

<a id="m06"></a>

### 06．玩家存档与数据模型

给业务提供容易使用的玩家对象，并清楚规定哪些数据需要保存。

参考方向：采用 Alloy 的 Bean 字段模型与变更追踪；普通业务按需加载，关键已提交状态外置到 Redis/MySQL，不依赖单个业务进程长期持有。数据权威、正式提交和失败恢复吸收 gameKit 的约束；本地缓存与临时对象仍需限制内存。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 06.01 | 字段统一声明 | 登记等级、材料等字段的类型和初始值，减少反复读取、转换和复制。 | 基础 |
| 06.02 | 数据用途标记 | 区分只保存在服务器、需要同步给本人、可以公开给其他玩家的字段。 | 基础 |
| 06.03 | 权威来源 | 普通玩法热档以 Redis 为依据，货币、订单和交付凭据按职责保存到 MySQL；业务进程内存及可重建缓存不作为最终账本。 | 基础 |
| 06.04 | 只读与可写对象 | 查看别人资料时只能读，避免无意修改别人的存档。 | 基础 |
| 06.05 | 按需加载 | 需要哪些部分就读哪些部分，避免每个小操作都加载全部历史数据。 | 基础 |
| 06.06 | 变更追踪 | 自动记录本次业务改了哪些字段，但只在统一提交成功后正式生效。 | 基础 |
| 06.07 | 旧档补默认值 | 新增字段时让老玩家有合理默认值，不能直接重建整份档案覆盖旧进度。 | 基础 |
| 06.08 | 旧档升级 | 按版本逐步转换历史数据，失败可停止并定位，避免全服同时重算。 | 运营 |
| 06.09 | 大集合与冷数据 | 背包、历史记录适当拆分；长期不活跃存档可迁到成本更低的存储。 | 扩展 |
| 06.10 | 业务进程状态外置 | 玩家关键存档和操作凭据不只保存在某个业务进程里；进程退出或替换后，其他获授权实例可从 Redis/MySQL 加载已提交状态。 | 基础 |
| 06.11 | 请求级加载与内存回收 | 按需加载业务数据，请求结束后释放不再使用的对象；为本地缓存、并发请求和大集合设置上限，避免对象一直积存在进程内存。 | 基础 |

<a id="m07"></a>

### 07．安全提交与防重复执行

保证材料不会凭空丢失，同一操作也不会因为重试执行两次。

参考方向：吸收 gameKit 的用户锁、版本保护、事务和 outbox 保障，接入 Alloy 风格的业务入口，并验证并发、重复请求及失败恢复行为。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 07.01 | 操作提交边界 | 把一次操作涉及的修改组织在一起，例如扣材料和升级不能只成功一半。 | 基础 |
| 07.02 | 同一玩家并发控制 | 同一玩家同时点击多个按钮时，有序处理冲突，避免后一笔覆盖前一笔。 | 基础 |
| 07.03 | 旧请求写入保护 | 旧进程恢复或旧请求迟到时，不能把新进度写回成旧进度。 | 基础 |
| 07.04 | 重复操作识别 | 网络重试携带同一操作编号或版本条件，不重复扣款和发奖。 | 基础 |
| 07.05 | 持久结果凭证 | 对付款、领取等奖励操作保存结果依据；不能只依靠很快过期的内存缓存去重。 | 按需 |
| 07.06 | 跨存储可靠交付 | 余额和道具分开存储时，在权威结果的同一次原子提交中保存交付凭据；独立消费者重试补齐，不能先扣款再单独入队。 | 按需 |
| 07.07 | 提交后通知 | 数据保存成功后再通知客户端成功；跨系统尚未完成则明确显示处理中。 | 基础 |
| 07.08 | 副作用补偿 | 已经调用外部系统的操作不能假装撤回；通过补偿、退款或人工处理完成闭环。 | 按需 |
| 07.09 | 失败资源释放 | 业务、保存或通知发生错误时，锁与连接都要释放，不能让玩家永久卡住。 | 基础 |

<a id="m08"></a>

### 08．客户端状态自动同步

玩家数据变化后界面自动更新，业务不重复返回整份角色数据。

参考方向：玩家长期数据采用 Alloy 的 Mod/Change 自动同步思路，并统一到安全提交成功之后；gameKit/Colyseus Schema 用于实时房间状态，避免同一字段由两套同步链路负责。

| 编号 | 子功能 | 业务描述：具体要做到什么 | 建设标记 |
|---|---|---|---|
| 08.01 | 首次完整快照 | 玩家进入游戏时收到自己有权限查看的完整当前状态。 | 基础 |
| 08.02 | 自动增量通知 | 等级或背包改变后只发送需要更新的部分，业务无需逐接口拼接玩家响应。 | 基础 |
| 08.03 | 断线后的补齐 | 重连时根据版本补差异；缺失过多时重新取完整快照。 | 基础 |
| 08.04 | 重复与乱序处理 | 旧消息迟到不覆盖新消息，同一更新收到两次也不会多加一次材料。 | 基础 |
| 08.05 | 默认值与删除语义 | 能区分没传这个字段、字段值是零、字段被删除，避免界面残留旧数据。 | 基础 |
| 08.06 | 同步权限 | 只同步本人数据或允许公开的字段，不把后台标记、凭证和他人私有数据发给玩家。 | 基础 |
| 08.07 | 多连接及多进程通知 | 记录玩家当前连接所在实例，跨进程或跨机器把更新送到正确连接；重连、实例替换后更新路由并补齐状态，避免只通知旧连接。 | 扩展 |
| 08.08 | 客户端模型与界面刷新 | 提供统一接收器更新客户端数据，页面订阅数据变化，不到处手写网络回调。 | 基础 |
